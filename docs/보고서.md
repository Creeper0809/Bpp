# B++ 알고리즘 최적화 언어 및 온라인 컴파일러 플랫폼 캡스톤 작품 보고서

## 1. 연구 배경 및 목적

소프트웨어 교육에서 컴파일러와 프로그래밍 언어 구현은 학습 난도가 높은 영역에 속한다. 일반적인 프로그래밍 수업에서는 소스 코드를 작성하고 실행 결과를 확인하는 과정이 중심이 되지만, 컴파일러 수업이나 언어 구현 학습에서는 그보다 더 안쪽의 과정을 이해해야 한다. 하나의 프로그램은 단순히 입력된 문자열 그대로 실행되는 것이 아니라, 먼저 토큰으로 분해되고, 문법 구조를 나타내는 AST(Abstract Syntax Tree)로 구성되며, 이후 중간 표현(IR), SSA(Static Single Assignment), 기계 독립 또는 기계 의존 표현을 거쳐 최종적으로 어셈블리 또는 실행 파일로 내려간다. 그러나 대부분의 온라인 실행기와 온라인 저지는 이 중 마지막 단계인 실행 결과만 보여준다. 사용자는 프로그램이 성공적으로 동작했는지, 오답이 났는지, 컴파일 오류가 발생했는지만 알 수 있을 뿐, 코드가 내부에서 어떤 구조로 해석되었고 어느 단계에서 문제가 발생했는지는 직접 관찰하기 어렵다.

이러한 한계는 특히 컴파일러를 배우는 학생에게 큰 장벽이 된다. 예를 들어 조건문, 반복문, 함수 호출, 배열 접근, 문자열 출력과 같은 구문은 소스 코드에서는 익숙한 형태로 보이지만, 컴파일러 내부에서는 서로 다른 노드와 제어 흐름, 임시 값, 레지스터 조작으로 변환된다. 학습자가 이 변환 과정을 직접 확인할 수 없다면 컴파일러 이론은 책이나 강의 자료 속 개념으로만 남기 쉽다. 반대로 소스 코드와 컴파일러 산출물을 한 화면에서 함께 볼 수 있다면, 학습자는 자신이 작성한 코드가 AST에서는 어떤 계층 구조를 이루고, SSA에서는 어떤 값의 흐름으로 정리되며, ASM에서는 어떤 명령어 묶음으로 변환되는지 즉시 비교할 수 있다. 본 프로젝트는 바로 이 지점을 문제의식으로 삼았다.

또 다른 문제의식은 알고리즘 학습에서 언어와 컴파일러가 수행하는 역할이 충분히 드러나지 않는다는 점이다. 알고리즘 문제 풀이에서는 정답 여부뿐 아니라 시간복잡도, 공간복잡도, 자료구조 선택, 메모리 할당 방식이 매우 중요하다. 그러나 대부분의 언어와 실행 환경은 사용자가 작성한 코드가 왜 시간 초과에 가까운지, 어떤 루프가 비용을 지배하는지, 어떤 컨테이너 사용이 메모리를 증가시키는지, 어떤 함수 호출이 최적화되지 못했는지를 컴파일 단계에서 설명하지 않는다. 본 프로젝트는 B++를 알고리즘에 최적화된 언어로 발전시키기 위해, 컴파일러가 코드의 비용 구조를 분석하고 이를 source range와 연결하여 사용자에게 설명할 수 있는 기반을 마련하고자 하였다. 즉 본 연구의 대상은 웹 컴파일러 서비스뿐 아니라 B++ 언어와 그 언어를 구현하는 컴파일러 자체이다.

본 프로젝트의 목표는 브라우저 기반 B++ 온라인 컴파일러를 구현하여, 사용자가 별도의 로컬 개발 환경을 설치하지 않고도 코드를 작성하고, 컴파일하고, 실행하고, 문제를 풀이할 수 있도록 하는 것이다. 동시에 B++ 컴파일러를 AST, SSA, IR, ASM, source map, optimization metadata를 구조화해서 제공하는 연구용 컴파일러로 확장하는 것도 주요 목표이다. 여기서 B++는 본 캡스톤의 핵심 대상 언어이며, 단순한 실행 지원을 넘어 알고리즘 풀이에 필요한 시간복잡도와 공간복잡도 관점의 분석, source-aware 내부 산출물, 계약형 최적화 모델을 지향한다. 또한 실제 사용 가능한 웹 서비스가 되기 위해서는 코드 편집기만으로 충분하지 않다. 사용자는 자신의 코드를 저장할 수 있어야 하고, 문제를 풀고 제출할 수 있어야 하며, 제출 결과를 다시 확인할 수 있어야 한다. 계정을 잃어버렸을 때 복구할 수 있어야 하고, 다른 사용자와 문제별로 질문을 나눌 수 있어야 하며, 서버에서는 사용자 코드 실행이 안전하게 격리되어야 한다. 따라서 본 작품은 B++ 언어와 컴파일러, 온라인 IDE, 온라인 저지, 컴파일러 시각화 도구, 학습 커뮤니티, 운영용 큐 조회 기능을 하나의 서비스로 통합하는 방향으로 설계하였다.

구체적으로 본 연구는 웹 환경에서 B++, C, C++, Python, Java, JavaScript 코드를 작성하고 실행할 수 있는 통합 IDE를 구현하는 것을 첫 번째 목표로 두었다. 두 번째 목표는 B++ 컴파일러의 AST, SSA, IR, ASM 산출물을 사용자가 직접 볼 수 있도록 하여 컴파일 과정을 시각적으로 이해하게 하는 것이다. 세 번째 목표는 B++ 컴파일러가 source-aware JSON, stable id, source range, generated metadata를 제공하도록 하여 웹 프론트엔드가 추정이 아니라 컴파일러가 보장하는 정보를 기반으로 분석 UI를 구성하게 하는 것이다. 네 번째 목표는 시간복잡도와 공간복잡도 budget, loop 분석, allocation 분석, alias 분석, escape 분석을 연결하여 향후 계약형 알고리즘 언어로 발전할 수 있는 기반을 마련하는 것이다. 다섯 번째 목표는 문제 풀이, 예제 채점, 전체 채점, 제출 이력, 리더보드를 제공하여 단순 실행기보다 목표 지향적인 학습 경험을 제공하는 것이다. 여섯 번째 목표는 사용자 코드가 서버에서 실행되는 만큼 Docker 샌드박스를 이용해 실행 환경을 격리하고, 자원 제한과 네트워크 제한을 적용하여 보안성과 운영 안정성을 확보하는 것이다. 마지막으로 커뮤니티, 비밀번호 재설정, 컴파일 큐, 자동 저장, 서버 저장 등 실제 서비스에서 사용자가 기대하는 기능을 포함하여 데모 수준을 넘어 제품에 가까운 완성도를 확보하고자 하였다.

## 2. 프로젝트의 범위

본 프로젝트의 범위는 단순한 코드 실행기를 제작하는 데 머무르지 않는다. 처음부터 목표로 삼은 것은 "웹에서 실행되는 B++ 학습 플랫폼"이었으며, 그 안에는 B++ 언어와 컴파일러 구현, 코드 편집, 컴파일, 실행, 시각화, 문제 풀이, 채점, 제출 관리, 커뮤니티, 배포 운영이 모두 포함된다. 일반적인 온라인 컴파일러는 사용자가 코드를 붙여 넣고 실행 결과를 확인하는 기능에 집중한다. 일반적인 온라인 저지는 문제를 풀고 정답 여부를 확인하는 기능에 집중한다. 본 작품은 이 둘을 결합하면서도 B++ 컴파일러 내부 구조와 최적화 근거를 함께 보여주는 것을 핵심 차별점으로 삼았다.

컴파일러 영역에서의 범위는 B++ 소스 코드를 파싱하여 AST를 만들고, lowering과 type/shape 분석을 거쳐 SSA 기반 중간 표현을 생성하며, 여러 최적화 pass와 backend를 통해 ASM 또는 실행 파일로 낮추는 전체 흐름을 포함한다. 또한 컴파일러가 내부 산출물을 단순 문자열 dump로만 내보내는 것이 아니라, 웹 컴파일러가 직접 사용할 수 있는 JSON 형태로 AST, IR, SSA, ASM, source map을 제공하도록 하는 작업도 포함하였다. 이 JSON에는 schemaVersion, source range, stable id, generated 여부, SSA instruction id 같은 정보가 포함되어야 하며, 이는 소스 코드 선택과 컴파일 산출물 하이라이트를 정확하게 연결하기 위한 필수 조건이다.

언어 설계 영역에서는 B++를 알고리즘 문제 풀이에 적합한 언어로 발전시키는 것을 범위에 포함하였다. 여기에는 `number`와 같은 고수준 수치 타입, slice와 Vec 기반 범위 증명, tagged metadata를 이용한 메모리 상태 추적, 함수 단위 escape analysis, MemorySSA와 alias 분석, loop optimizer, complexity budget 기반 report 구조가 포함된다. 이 범위는 모든 시간복잡도와 공간복잡도를 완전 자동 증명하는 것을 의미하지 않는다. 대신 알고리즘 코드에서 자주 등장하는 반복문, 컨테이너, 표준 라이브러리 호출, 재귀, 메모리 할당 패턴을 컴파일러가 보수적으로 분석하고, 증명 가능한 부분과 증명하지 못한 부분을 source range와 함께 설명할 수 있는 기반을 만드는 것을 목표로 한다.

웹 IDE 영역에서는 Monaco Editor 기반 코드 편집기, 언어 선택, 컴파일, 실행, 터미널 입출력, 자동 저장 기능을 포함하였다. Monaco Editor를 사용한 이유는 브라우저 환경에서도 VS Code와 유사한 편집 경험을 제공할 수 있고, 구문 강조, 선택 범위, 스크롤, 복사 같은 기본 편집 동작을 일관되게 제공하기 때문이다. 컴파일러 시각화 영역에서는 AST, SSA, IR, ASM 출력 표시를 제공하고, 사용자가 소스 코드 일부를 선택했을 때 해당 범위와 관련된 컴파일 산출물을 하이라이트하도록 구성하였다. 이 기능은 B++ 컴파일러가 JSON source map을 제공하는 방식과 프론트엔드의 범위 겹침 판정 로직이 함께 동작해야 가능하다.

문제 풀이 영역에서는 문제 목록, 난이도 필터, 태그 필터, 검색, 문제 상세, 예제 채점, 전체 채점을 포함하였다. 제출 관리 영역에서는 제출 이력 조회, 사용자별 필터, 문제별 필터, 판정 상태 표시, 점수 기록을 제공하였다. 컴파일 큐 영역은 사용자가 작성한 코드의 컴파일, 실행, 채점 작업이 어떤 상태로 처리되었는지를 확인하기 위한 기능이다. 여기에는 문제별 집계, 사용자별 집계, 작업 종류별 필터, 판정별 필터가 포함된다. 사용자 기능으로는 회원가입, 로그인, 프로필, 비밀번호 재설정, 서버 저장을 포함하였고, 커뮤니티 기능으로는 공지, 문제별 게시판, 자유 게시판, Markdown 및 수식 렌더링, 게시글 수정과 삭제를 포함하였다. 운영 기능으로는 Docker 샌드박스, PostgreSQL 기반 데이터 보존, Nginx 프록시, GitHub Actions 배포를 범위에 포함하였다.

다만 모든 기능을 무한히 확장하는 것은 본 캡스톤의 현실적인 범위를 넘어선다. 따라서 본 프로젝트는 교육용 컴파일러 서비스의 핵심 흐름과 B++ 컴파일러의 핵심 분석 기반을 실제 사용 가능한 형태로 구현하는 데 초점을 두었다. 대규모 동시 채점, 반 단위 과제 관리, 유료 과금, 세밀한 관리자 통계, 대회 운영 기능, 고급 부정 제출 탐지와 같은 서비스 운영 기능은 향후 확장 범위로 남겨두었다. 컴파일러 측면에서도 모든 알고리즘의 복잡도를 완전 증명하거나 모든 최적화를 완성하는 것은 후속 연구 대상으로 보았다. 즉 본 작품의 범위는 "실제 서버에 배포하여 사용자가 접속하고, 코드를 실행하고, 문제를 제출하고, 컴파일러 내부 결과와 최적화 분석 기반을 확인할 수 있는 수준"까지이며, 대규모 상용 온라인 저지의 모든 운영 정책과 완전한 정적 복잡도 증명 시스템을 완성하는 것은 후속 연구 대상으로 보았다.

## 3. 연구 가설 및 기대 효과

본 프로젝트는 네 가지 핵심 가설을 바탕으로 설계하였다. 첫째, 컴파일러 내부 산출물을 텍스트와 그래프 형태로 함께 제공하면 학습자가 단순 실행 결과만 확인하는 경우보다 컴파일 과정을 더 명확하게 이해할 수 있다는 가설이다. 특히 AST는 프로그램의 문법 구조를 계층적으로 보여주고, SSA는 값의 정의와 사용 관계를 비교적 명확하게 드러낸다. IR과 ASM은 고수준 언어가 점차 낮은 수준의 표현으로 변환되는 과정을 보여준다. 따라서 학습자는 자신이 작성한 B++ 코드가 어떤 내부 표현으로 바뀌는지 확인하면서, 컴파일러 교재에서 배운 개념을 실제 코드와 연결할 수 있다.

둘째, 알고리즘에 최적화된 언어와 계약형 컴파일러를 함께 제공하면 학습자가 단순히 정답 여부만 확인하는 것이 아니라 풀이의 비용 구조를 더 잘 이해할 수 있다는 가설이다. 알고리즘 문제에서 시간 초과와 메모리 초과는 대개 반복문 구조, 자료구조 선택, 불필요한 복사, 힙 할당, 함수 호출 비용에서 발생한다. B++ 컴파일러가 loop trip count, MemorySSA, alias proof, escape analysis, allocation metadata, optimization budget을 분석하고 이를 source range와 연결하면, 사용자는 어떤 코드가 시간복잡도 또는 공간복잡도 예산을 악화시키는지 더 이른 단계에서 확인할 수 있다. 이는 온라인 저지의 최종 판정 중심 피드백을 컴파일러의 구조적 피드백으로 확장한다.

셋째, 웹 기반 IDE와 온라인 저지를 결합하면 학습자가 코드 작성, 실행, 제출, 피드백 확인을 하나의 화면 흐름 안에서 수행할 수 있다는 가설이다. 기존 학습 환경에서는 로컬에 컴파일러를 설치하고, 편집기를 설정하고, 터미널에서 명령어를 실행하고, 온라인 저지 사이트에 코드를 복사하여 제출하는 과정이 분리되는 경우가 많다. 이러한 분리는 학습자의 집중을 흐트러뜨리고, 환경 설정에 익숙하지 않은 학생에게 진입 장벽이 된다. 본 작품은 브라우저 안에서 편집, 실행, 문제 풀이, 제출 이력 확인이 이어지도록 하여 반복 실험의 부담을 낮추고자 하였다.

넷째, 사용자 코드 실행을 컨테이너 샌드박스로 격리하면 온라인 코드 실행 서비스의 주요 위험을 줄일 수 있다는 가설이다. 온라인 컴파일러는 사용자가 작성한 임의의 코드를 서버에서 실행해야 하므로 무한 루프, 과도한 메모리 사용, 파일 시스템 접근, 네트워크 접근, 프로세스 남용 같은 위험을 고려해야 한다. 본 프로젝트는 Docker 컨테이너를 실행 단위로 사용하고, 네트워크 비활성화, read-only 파일 시스템, CPU 및 메모리 제한, PID 제한, capability 제거, no-new-privileges 옵션을 적용하여 서버 전체에 대한 영향을 최소화하였다. 이러한 구조는 교육용 서비스가 실제 서버에서 운영되기 위한 기본 조건이다.

이러한 설계를 통해 기대한 효과는 크게 다섯 가지이다. 먼저 학습자는 B++ 코드를 작성하면서 AST, SSA, IR, ASM 변환 결과를 즉시 확인할 수 있으므로, 코드와 컴파일러 내부 구조 사이의 대응 관계를 경험적으로 학습할 수 있다. 다음으로 B++ 컴파일러의 complexity budget과 optimization metadata를 활용하면 사용자는 알고리즘 풀이의 시간복잡도와 공간복잡도를 더 구체적으로 이해할 수 있다. 세 번째로 문제 풀이와 채점을 통해 단순한 언어 실험을 넘어 목표 지향적인 프로그래밍 학습이 가능해진다. 또한 제출 이력, 컴파일 큐, 리더보드는 개인 학습 기록과 서비스 운영 상태를 함께 보여주어 사용자는 자신의 진행 상황을 확인하고 운영자는 시스템 상태를 파악할 수 있다. 마지막으로 커뮤니티는 문제별 질의응답과 풀이 토론을 가능하게 하여 사용자가 혼자 실행 결과만 확인하는 데 그치지 않고, 오류 원인과 접근 방식을 공유하는 학습 흐름으로 확장되도록 한다.

## 4. 작품 개요

### 4.1 작품의 정의 및 특징

B++ Online Compiler는 브라우저에서 실행되는 온라인 컴파일러 및 학습 플랫폼이다. 사용자는 웹 IDE에서 코드를 작성하고, 버튼을 눌러 컴파일과 실행을 수행하며, 문제 페이지에서 제출과 채점을 진행할 수 있다. 일반적인 온라인 컴파일러와 다른 점은 본 작품이 B++ 컴파일러의 내부 산출물을 적극적으로 노출한다는 데 있다. 사용자는 AST, SSA, IR, ASM을 별도의 패널에서 확인할 수 있고, 소스 코드의 특정 부분을 선택하여 해당 부분과 관련된 산출물 라인을 확인할 수 있다. 이 기능은 단순히 "코드가 실행된다"는 결과를 넘어 "코드가 어떻게 번역된다"는 과정을 보여준다.

작품의 첫 번째 특징은 통합 코드 편집 환경이다. Monaco Editor를 기반으로 구현했기 때문에 사용자는 웹 브라우저에서도 익숙한 코드 편집 경험을 얻을 수 있다. 파일명 표시, 코드 복사, 자동 저장 상태 표시, 언어 선택, 컴파일과 실행 버튼이 IDE 화면에 결합되어 있으며, 메인 화면에서 작성한 코드와 문제별 풀이 코드는 서로 분리되어 저장된다. 이는 사용자가 실험용 코드와 특정 문제 풀이 코드를 혼동하지 않도록 하기 위한 설계이다.

두 번째 특징은 다중 언어 실행이다. 본 작품의 중심 언어는 B++이지만, 학습 플랫폼으로서 C, C++, Python, Java, JavaScript 실행도 함께 지원한다. 이를 통해 사용자는 알고리즘 문제를 여러 언어로 실험할 수 있고, B++의 동작을 다른 언어와 비교할 수 있다. 다만 컴파일러 내부 산출물 시각화는 B++ 컴파일러에 특화된 기능이므로 B++ 언어에서 가장 풍부하게 제공된다.

세 번째 특징은 컴파일러 내부 시각화와 소스맵 기반 대응 관계 표시이다. AST와 SSA는 그래프 형태로 표시하고, IR과 ASM은 라인 기반 출력으로 제공한다. 특히 ASM 출력은 컴파일러가 생성한 JSON source map의 source range, byte offset, stable range id, SSA instruction id, segment 정보를 활용하도록 설계하였다. 초기 구현에서는 문자열 검색에 가까운 방식으로 관련 라인을 추정했기 때문에 동일한 변수명이나 유사한 코드가 반복될 때 오탐이 발생할 수 있었다. 이후 컴파일러가 source range를 직접 제공하도록 개선되면서 프론트엔드는 선택 범위와 source range의 overlap을 기준으로 보다 엄격하게 하이라이트할 수 있게 되었다.

네 번째 특징은 문제 풀이와 채점 기능이다. 본 작품은 온라인 컴파일러인 동시에 온라인 저지이므로, 사용자는 문제 목록에서 문제를 선택하고, 설명과 예제를 확인한 뒤, 문제별 코드 편집 화면에서 풀이를 작성할 수 있다. 채점은 "예제 채점"과 "채점"으로 구분하였다. 예제 채점은 공개된 예제를 기준으로 사용자가 먼저 확인할 수 있는 단계이고, 채점은 전체 테스트를 기준으로 최종 결과를 판단하는 단계이다. 이 표현은 숨겨진 테스트 케이스의 개수나 내부 구조를 직접 노출하지 않으면서도 사용자가 제출 결과를 이해할 수 있도록 한다.

다섯 번째 특징은 실서비스형 부가 기능이다. 로그인, 회원가입, 서버 저장, 제출 이력, 컴파일 큐, 리더보드, 커뮤니티, 비밀번호 재설정이 포함되어 있다. 단순 캡스톤 데모라면 코드 실행 화면만 있어도 기능을 설명할 수 있지만, 실제 사용자가 지속적으로 쓰는 서비스가 되려면 계정과 데이터 보존, 피드백 기록, 게시판, 장애 대응 흐름이 필요하다. 본 작품은 이러한 요소를 포함함으로써 제품 수준의 사용 흐름을 갖추고자 하였다.

### 4.2 작품의 기능 및 구조

시스템은 크게 프론트엔드, 백엔드, 컴파일/실행 샌드박스, 데이터베이스, 배포 프록시로 구성된다. 프론트엔드는 사용자가 직접 보는 화면과 조작 흐름을 담당한다. React와 TypeScript를 기반으로 화면을 구성하고, Vite를 사용하여 개발과 빌드를 수행하였다. Monaco Editor는 코드 편집을 담당하고, Zustand는 코드 상태, 컴파일 결과, 실행 상태, 터미널 상태, 테마, 자동 저장 상태를 관리한다. AST와 SSA 그래프는 React Flow를 사용하여 표시하고, 노드 배치에는 Dagre 기반 자동 배치를 적용하였다.

백엔드는 FastAPI 기반으로 구현하였다. REST API는 컴파일, 실행, 문제, 제출, 커뮤니티, 인증, 관리자성 데이터 조회를 담당하고, WebSocket은 터미널 세션과 같이 지속적인 입출력이 필요한 기능에 사용하였다. Pydantic schema는 요청과 응답의 형태를 검증하고, SQLAlchemy ORM은 사용자, 문제, 제출, 댓글, 점수, 저장 코드 같은 영속 데이터를 관리한다. 백엔드의 중요한 역할은 사용자 입력을 신뢰하지 않고 검증한 뒤, 샌드박스 실행에 필요한 임시 작업 디렉터리와 제한 설정을 구성하는 것이다.

컴파일과 실행 계층은 Docker 컨테이너 기반으로 구성된다. B++ 코드는 B++ Compiler로 컴파일되고, C와 C++은 GCC 계열 도구, Java는 OpenJDK, JavaScript는 Node.js, Python은 Python 런타임을 사용한다. 사용자 코드는 서버 프로세스에서 직접 실행되지 않고 컨테이너 안에서 실행된다. 이때 네트워크를 비활성화하고, 파일 시스템을 제한하고, CPU와 메모리 사용량을 제한하여 악의적이거나 실수로 작성된 코드가 서버 전체에 영향을 주지 않도록 하였다.

데이터 저장은 PostgreSQL을 사용하였다. 초기에는 컨테이너와 데이터 볼륨 구성 문제로 인해 서버 재배포 시 데이터가 초기화되는 문제가 있었지만, 이후 공유 PostgreSQL 네트워크와 volume 기반 데이터 보존 구조를 정리하여 한쪽 컨테이너가 갱신되어도 동일한 데이터베이스를 바라보도록 수정하였다. 배포는 Nginx와 Docker Compose를 사용한다. 서비스는 `/webcompiler/` 경로에서 제공되며, 프론트엔드 정적 파일과 백엔드 API는 Nginx 프록시를 통해 연결된다. GitHub Actions는 빌드와 테스트가 통과한 변경만 서버 배포 스크립트로 전달하도록 구성하였다.

| 계층 | 사용 기술 | 역할 |
|---|---|---|
| 프론트엔드 | React, TypeScript, Vite, Monaco Editor, Zustand, React Flow | IDE, 문제, 커뮤니티, 리더보드, 큐 화면 구현 |
| 백엔드 | FastAPI, Pydantic, SQLAlchemy | REST API, WebSocket 터미널, 채점, 사용자/문제/제출 관리 |
| 컴파일/실행 | Docker, B++ Compiler, GCC, OpenJDK, Node.js, Python | 사용자 코드 격리 컴파일 및 실행 |
| 데이터 저장 | PostgreSQL, SQLAlchemy ORM | 사용자, 문제, 제출, 댓글, 점수, 코드 프로젝트 저장 |
| 배포 | Nginx, Docker Compose, GitHub Actions | `/webcompiler/` 경로 배포, blue-green 방식 컨테이너 전환 |

프론트엔드와 백엔드는 명확한 API 경계를 통해 연결된다. 사용자가 컴파일 버튼을 누르면 프론트엔드는 현재 코드, 언어, 파일명, 실행 옵션을 API 요청으로 전송한다. 백엔드는 요청을 검증하고 샌드박스 컨테이너를 생성하여 코드를 컴파일한다. 컴파일 결과는 성공 여부, 오류 목록, AST/SSA/IR/ASM 데이터, 실행 시간, 출력 결과로 구조화되어 다시 프론트엔드에 전달된다. 문제 제출의 경우 백엔드는 문제에 등록된 예제와 채점 케이스를 순차적으로 실행하고, 판정 결과를 제출 테이블과 사용자 점수에 반영한다. 이러한 구조는 IDE 기능과 온라인 저지 기능이 동일한 실행 기반을 공유하도록 하여 유지보수성을 높인다.

### 4.3 B++ 컴파일러와 알고리즘 최적화 언어 설계

본 작품의 핵심은 웹에서 코드를 실행하는 서비스만이 아니라, 알고리즘 문제 해결에 최적화된 새로운 언어와 그 언어를 뒷받침하는 컴파일러를 함께 개발하는 데 있다. B++는 단순히 기존 언어의 문법을 약간 바꾼 실험용 언어가 아니라, 알고리즘 풀이에서 반복적으로 등장하는 성능 문제를 언어와 컴파일러가 함께 해결하도록 설계된 언어이다. 온라인 저지 환경에서는 같은 정답 코드라도 시간 제한과 메모리 제한을 만족하는지가 중요하다. 따라서 언어는 표현력이 높아야 할 뿐 아니라, 사용자가 작성한 코드의 시간복잡도와 공간복잡도가 어떻게 형성되는지 컴파일러가 분석하고, 필요하면 최적화하며, 가능하면 계약 형태로 설명할 수 있어야 한다.

일반적인 프로그래밍 언어는 성능을 대부분 사용자의 책임으로 둔다. 사용자가 `vector`, `list`, `map`, 재귀, 정렬, 큰 정수, 문자열, 슬라이스를 어떻게 사용하는지에 따라 실행 시간과 메모리 사용량이 달라지지만, 컴파일러는 대개 기계어를 빠르게 만드는 지역 최적화에 집중한다. 반면 B++가 지향하는 방향은 알고리즘 자체의 복잡도와 자료구조 사용 비용을 컴파일러가 더 적극적으로 이해하는 것이다. 예를 들어 반복문이 입력 크기 `n`에 대해 몇 번 실행될 수 있는지, 슬라이스 접근이 범위 증명 안에 있는지, 컨테이너가 루프 안에서 재할당되는지, 어떤 함수 호출이 순수한 계산인지, 어떤 객체가 힙으로 escape하지 않고 스택이나 arena에 머물 수 있는지를 컴파일러가 추적한다. 이 정보는 단순한 성능 힌트가 아니라, 알고리즘 코드의 비용 구조를 설명하는 근거가 된다.

B++ 언어 설계에서 중요한 점은 "편한 문법"과 "예측 가능한 비용"을 동시에 추구한다는 것이다. Python은 표현력이 높지만 수치와 객체가 대부분 무거운 런타임 표현을 거치기 쉽고, C++은 성능 제어력이 강하지만 초심자가 타입과 메모리 전략을 직접 관리해야 한다. Rust는 소유권 모델로 메모리 안전성을 강하게 보장하지만 알고리즘 수업에서 학습 부담이 높을 수 있고, Zig는 comptime을 통해 강력한 컴파일 타임 계산을 제공하지만 온라인 저지 학습 흐름에 특화된 복잡도 피드백을 기본 목표로 하지는 않는다. B++는 이 장점들을 참고하되, 알고리즘 풀이에서 자주 필요한 수치 타입, slice, Vec, 표준 알고리즘, 입력 처리, 출력 처리, 복잡도 분석을 컴파일러가 함께 이해하는 방향을 잡았다.

| 언어 설계 요소 | B++에서의 의도 | 알고리즘 학습에서의 효과 |
|---|---|---|
| `number` 수치 타입 | 정수, 큰 정수, 실수, 복소수 표현을 하나의 고수준 수치 모델로 통합 | overflow와 타입 선택 부담을 낮추되 내부 표현은 범위와 연산에 맞게 최적화 |
| slice와 Vec | 길이, 범위, capacity, growth 정보를 컴파일러가 추적 가능한 컨테이너 축으로 사용 | bounds check 제거, 불필요한 복사 탐지, 공간복잡도 report에 활용 |
| tagged metadata | 값의 lifecycle, ownership, escape, shape 정보를 포인터 또는 객체 metadata와 연결 | 스택 배치, arena 배치, GC 후보 분리, barrier 생략 같은 메모리 최적화 근거 제공 |
| source-aware JSON | AST, IR, SSA, ASM, 최적화 결과를 원본 source range와 stable id로 연결 | 웹 IDE에서 문자열 추정이 아니라 컴파일러가 보장하는 매핑으로 설명 가능 |
| complexity contract | 함수나 블록의 시간복잡도·공간복잡도 예산을 컴파일러 분석 대상으로 유지 | 시간 초과와 메모리 초과 후보를 실행 전 단계에서 구조적으로 설명 |
| 표준 라이브러리 summary | sort, search, reduce, container operation의 비용 요약을 컴파일러가 읽을 수 있게 함 | 라이브러리 호출을 블랙박스로 두지 않고 전체 풀이 비용 분석에 포함 |

현재 구현된 범위와 향후 확장 범위도 구분할 필요가 있다. 본 프로젝트는 모든 알고리즘 복잡도를 완전 자동 증명하는 언어를 완성했다고 주장하지 않는다. 대신 source-aware 컴파일러 출력, SSA 기반 최적화, tagged metadata, loop/alias/escape 분석 기반, complexity report 구조를 구현하여 계약형 알고리즘 언어로 확장할 수 있는 토대를 마련하였다.

| 구분 | 현재 구현한 기반 | 향후 확장 방향 |
|---|---|---|
| source map | AST/SSA/ASM line에 source range, stable id, generated metadata를 연결하는 JSON 출력 | expression/operand 단위 segment mapping과 AST-IR-SSA-ASM cross-navigation 강화 |
| 최적화 metadata | loop, alias, escape, allocator/lifecycle, number specialization에 필요한 분석 정보를 SSA pass에 축적 | 사용자가 읽을 수 있는 optimization report와 복잡도 증명 실패 사유 출력 |
| complexity budget | 시간·공간 budget을 컴파일러 계약으로 다루기 위한 report 모델과 분석 축 정의 | 실제 문법 또는 annotation과 연결하고 문제별 요구 복잡도와 채점 정책에 결합 |
| 메모리 정책 | stack-new, escape analysis, tagged lifecycle metadata, allocator 최적화 기반 구성 | GC nursery/old generation, moving/compaction, arena 정책을 언어 차원의 lifetime 규칙과 연결 |
| 웹 통합 | B++ 컴파일 산출물을 웹 IDE가 구조화해서 표시 | 복잡도 경고, 최적화 실패 위치, 메모리 budget 초과 후보를 문제 풀이 UI에 표시 |

| 비교 대상 | 강점 | B++가 차별화하려는 지점 |
|---|---|---|
| Python | 간결한 문법, 큰 정수와 리스트 사용 편의성 | 편의성은 유지하되 수치와 컨테이너 표현을 컴파일러가 정적으로 더 많이 최적화 |
| C++ | 강력한 성능, 풍부한 표준 라이브러리 | 낮은 수준의 타입·메모리 부담을 줄이고 복잡도 report를 언어 기능으로 제공 |
| Rust | 소유권 기반 메모리 안전성, zero-cost abstraction | 알고리즘 학습 친화성을 높이고 비용 budget과 source-aware 설명을 전면에 배치 |
| Zig | comptime과 명시적인 시스템 프로그래밍 모델 | 컴파일 타임 분석 아이디어를 알고리즘 문제 풀이와 복잡도 계약에 연결 |
| B++ | 알고리즘 풀이, compiler report, source-aware JSON, tagged metadata를 한 흐름으로 결합 | 정답 여부뿐 아니라 풀이의 비용 구조를 설명하는 계약형 알고리즘 언어 지향 |

이러한 목표를 위해 B++ 컴파일러는 "계약형 컴파일러" 모델을 지향한다. 여기서 계약이란 함수나 코드 블록이 만족해야 하는 시간복잡도, 공간복잡도, 메모리 사용 방식, 부작용 범위, alias 조건, 입력 크기 조건을 컴파일러가 다룰 수 있는 형태로 표현한 것이다. 예를 들어 어떤 함수가 `O(n log n)` 시간과 `O(n)` 공간 안에서 동작해야 한다는 요구가 있을 때, 컴파일러는 이 계약을 단순 주석으로 무시하지 않고 내부 메타데이터로 유지한다. 이후 AST, lowering, SSA, 최적화, ASM 생성 단계에서 이 계약을 가능한 한 보존하고, 최적화 결과가 계약을 만족하는지 또는 왜 증명하지 못했는지를 보고할 수 있도록 한다.

```text
목표 형태의 계약 예시

@complexity(time <= O(n log n), space <= O(n))
func solve(values: []i64) -> i64 {
    ...
}
```

위 예시는 최종적으로 지향하는 표현 방식이다. 중요한 점은 문법 자체보다 컴파일러가 이 계약을 어떻게 해석하느냐이다. `values.len`이 입력 크기 `n`에 해당한다고 추론하고, 반복문의 trip count를 추적하며, 정렬이나 탐색 같은 표준 라이브러리 호출의 비용 요약을 읽고, 임시 배열이나 힙 할당이 공간 예산을 초과하지 않는지 확인해야 한다. 즉 B++의 complexity contract는 단순한 문서화 주석이 아니라, 컴파일러의 분석 대상이다.

컴파일러가 사용자에게 돌려줄 report는 단순 경고 문자열이 아니라 구조화된 데이터여야 한다. 예를 들어 `solve` 함수가 `O(n log n)` 예산을 요구하는데 내부에서 `n` 길이 루프가 중첩되어 `O(n^2)` 후보가 발견되면, 컴파일러는 어느 루프가 문제인지, 어떤 분석 근거로 그렇게 판단했는지, 어떤 source range에 해당하는지 함께 내려줄 수 있어야 한다. 이 report가 JSON으로 제공되면 웹 IDE는 해당 루프를 직접 하이라이트하고, 사용자는 문제의 원인을 코드 위치와 함께 확인할 수 있다.

```json
{
  "schemaVersion": 1,
  "complexityReport": {
    "function": "solve",
    "declaredBudget": {
      "time": "O(n log n)",
      "space": "O(n)"
    },
    "inferredCost": {
      "time": "O(n^2)",
      "space": "O(n)"
    },
    "diagnostics": [
      {
        "kind": "time-budget-risk",
        "message": "중첩 반복문이 입력 길이 n에 대해 O(n^2) 후보로 분석되었습니다.",
        "sourceRanges": [
          {
            "file": "main.bpp",
            "startLine": 8,
            "startColumn": 5,
            "endLine": 15,
            "endColumn": 6
          }
        ],
        "evidence": [
          "outer loop trip count: values.len",
          "inner loop trip count: values.len"
        ]
      }
    ]
  }
}
```

| 계약 요소 | 의미 | 컴파일러가 확인해야 하는 정보 |
|---|---|---|
| 시간복잡도 예산 | 함수나 블록이 허용하는 연산 증가율 | 반복문 trip count, 재귀 깊이, 함수 호출 비용, 표준 라이브러리 summary |
| 공간복잡도 예산 | 입력 크기에 대해 허용되는 추가 메모리 증가율 | stack slot, heap allocation, container growth, temporary buffer |
| 메모리 lifecycle 계약 | 값이 stack, arena, heap, GC 영역 중 어디에 머무는지 | escape analysis, ownership tag, borrowed/pinned/immortal 상태 |
| alias 계약 | 두 포인터나 slice가 같은 메모리를 가리킬 수 있는지 | MemorySSA, slice proof, field offset, tagged metadata |
| 부작용 계약 | 함수 호출이 읽거나 쓰는 상태의 범위 | pure/read-only/write effect summary, call graph |
| 최적화 예산 | 컴파일 시간이 과도하게 증가하지 않도록 하는 한도 | pass별 반복 횟수, code size growth, specialization threshold |

시간복잡도와 공간복잡도 예산을 컴파일러 계약으로 다룬다는 것은 온라인 저지의 시간 제한과 메모리 제한을 더 이른 단계로 끌어올린다는 뜻이다. 일반적인 온라인 저지는 프로그램을 실제로 실행한 뒤 시간 초과나 메모리 초과를 판정한다. 이 방식은 단순하고 확실하지만, 왜 초과했는지는 설명하지 못한다. B++ 컴파일러는 실행 전 단계에서 "이 루프는 입력 길이에 선형으로 비례한다", "이 중첩 루프는 최악의 경우 `O(n^2)` 후보이다", "이 컨테이너 복사는 루프 내부에서 발생하므로 공간 예산을 악화시킬 수 있다"와 같은 구조적 정보를 만들 수 있다. 이러한 정보가 웹 컴파일러에 연결되면 사용자는 단순히 실패 판정을 받는 것이 아니라, 어떤 코드 구조가 복잡도 예산을 위반했는지 학습할 수 있다.

이 모델을 구현하기 위해 컴파일러 내부 표현은 source-aware 구조를 가져야 한다. 분석 결과가 아무리 정교해도 그것이 원본 코드의 어느 부분에서 발생했는지 사용자가 알 수 없다면 교육적 가치가 떨어진다. 따라서 B++ 컴파일러는 모든 AST 노드와 SSA instruction, ASM line에 source range와 stable id를 붙이는 방향으로 확장되었다. AST node id, origin node id, SSA instruction id, ASM line의 source range가 연결되면, 사용자는 웹 IDE에서 특정 코드를 선택했을 때 해당 코드가 어떤 SSA instruction을 만들고, 어떤 ASM line으로 내려갔으며, 어떤 최적화나 계약 분석의 대상이 되었는지 추적할 수 있다.

컴파일러 파이프라인은 다음과 같은 단계로 구성된다. 중요한 점은 각 단계가 독립적으로 끊어지는 것이 아니라, source range, stable id, origin id, generated 여부, optimization metadata를 계속 전달한다는 것이다.

```text
B++ source
  -> Lexer / Parser
  -> AST + SourceSpan + astNodeId
  -> Lowering + originNodeId
  -> Type / Shape / Number storage analysis
  -> SSA + use-def + MemorySSA + sourceRanges
  -> Optimization passes + optimization metadata
  -> Backend / ASM + SSA/IR instruction links
  -> Unified JSON + source map + complexity report
  -> Web IDE visualization / judge feedback
```

| 단계 | 역할 | 계약형 최적화와의 관계 |
|---|---|---|
| Lexer/Parser | 소스 코드를 토큰과 AST로 변환 | 모든 노드에 source span을 부여하여 이후 분석 결과를 원본 코드와 연결 |
| AST Lowering | 문법 설탕, `print`, `input`, `number`, method call 등을 내부 표현으로 변환 | 새로 생성된 노드가 원래 AST origin을 잃지 않도록 보존 |
| Type/Shape 분석 | 값의 타입, 크기, 포인터 깊이, 컨테이너 형태를 계산 | number storage, slice 길이, struct field offset, call signature를 최적화 근거로 제공 |
| SSA 생성 | 값을 단일 정의 기반 IR로 변환 | use-def chain, phi, branch, call을 통해 데이터 흐름과 제어 흐름을 분석 가능하게 함 |
| O1/O2 최적화 | SCCP, GVN, MemorySSA, loop optimizer, inlining 등을 수행 | 시간/공간 비용을 줄이고, 어떤 최적화가 적용되었는지 metadata로 남김 |
| Backend/ASM | 레지스터 할당, 기계 명령 생성, 런타임 호출 연결 | 최종 ASM line을 SSA instruction 및 source range와 연결 |
| JSON/Report 출력 | AST/IR/SSA/ASM/source map을 구조화된 JSON으로 출력 | 웹 컴파일러가 문자열 추정이 아니라 안정적인 매핑과 분석 UI를 구현하게 함 |

최적화 pass도 단순히 "빠르게 만든다"는 표현보다 어떤 알고리즘적 효과를 갖는지 구분해야 한다. B++의 최적화 pass는 코드 생성 품질을 높이는 동시에 complexity report의 근거를 만든다. 예를 들어 loop optimizer는 반복문을 빠르게 만드는 pass이면서 동시에 반복 횟수와 중첩 구조를 요약하는 분석 pass이다. escape analysis는 힙 할당을 줄이는 pass이면서 공간복잡도 report의 핵심 근거가 된다.

| 최적화 단계 | 대표 분석/변환 | 알고리즘 관점의 효과 | report에 남길 수 있는 근거 |
|---|---|---|---|
| Sparse Conditional Constant Propagation | 상수 조건, 도달 불가능 block 제거 | 입력과 무관한 죽은 경로 제거 | 제거된 branch와 원래 조건 source range |
| Global Value Numbering / CSE | 동일 계산을 하나의 값으로 합침 | 반복 계산 제거, 산술 비용 감소 | 합쳐진 expression id와 대체된 SSA id |
| MemorySSA / Alias proof | load/store 의존 관계 요약 | 불필요한 메모리 접근 제거, 안전한 hoist 판단 | alias proof 성공/실패 이유 |
| Loop analysis | induction variable, trip count, nested loop 탐지 | 시간복잡도 후보 계산 | `O(n)`, `O(n^2)` 같은 loop cost summary |
| Loop transformation | LICM, strength reduction, bounds check 제거 | 반복문 내부 비용 감소 | hoist된 instruction과 제거된 check |
| Inlining / IPA summary | 함수 간 pure/read-only/escape 정보 전파 | 작은 함수 호출 비용 제거, call cost 계산 | call site별 inlining 여부와 threshold |
| Escape / SROA | 객체를 stack slot 또는 SSA field 값으로 분해 | heap allocation 감소, 공간 사용량 감소 | stack lowering 성공 여부와 escape edge |
| Allocator/lifecycle policy | young/old/arena/pinned/immortal tag 연결 | 메모리 관리자 정책과 컴파일러 분석 연결 | allocation site별 lifecycle tag |

B++ 컴파일러의 SSA 최적화는 알고리즘 언어라는 목표와 직접 연결된다. 상수 전파와 상수 접기는 불필요한 계산을 제거하고, SCCP는 실제로 도달 가능한 제어 흐름만 따라가며 조건 분기를 줄인다. 전역 값 번호화와 공통식 제거는 반복되는 계산을 하나의 값으로 합치고, MemorySSA와 alias 분석은 같은 메모리를 다시 읽는 비용을 줄이거나 불필요한 store를 제거한다. 루프 최적화는 알고리즘 문제에서 가장 중요한 영역이다. 반복문은 시간복잡도의 핵심이므로, induction variable, trip count, loop invariant code, bounds check, reduction, vectorization 후보를 분석하는 것은 B++의 정체성과 맞닿아 있다.

특히 루프 최적화는 시간복잡도 계약을 구현하기 위한 기반이다. 컴파일러가 `for` 또는 `while` 루프의 반복 횟수를 추론할 수 있으면, 단순한 기계어 최적화를 넘어 알고리즘 비용을 요약할 수 있다. 예를 들어 `0 <= i < values.len` 형태의 루프는 입력 slice 길이에 선형으로 비례한다는 정보를 만들 수 있고, 내부에 또 다른 `values.len` 기반 루프가 있으면 이중 반복 후보로 표시할 수 있다. 또한 bounds check elimination은 공간 안전성과 실행 성능을 동시에 다룬다. 범위가 증명된 slice 접근은 매번 런타임 체크를 반복하지 않아도 되므로, 안전성을 포기하지 않고 반복문 성능을 높일 수 있다.

공간복잡도 계약은 메모리 관리자와 escape analysis, tagged metadata와 연결된다. 알고리즘 문제에서 메모리 초과는 대개 불필요한 복사, 루프 내부 할당, 컨테이너 growth, 큰 임시 버퍼 때문에 발생한다. B++ 컴파일러는 값이 함수 밖으로 escape하는지, 객체가 stack slot으로 낮춰질 수 있는지, arena에 둘 수 있는지, heap allocation이 필요한지, GC nursery 또는 old generation으로 분리할 수 있는지를 분석하는 방향으로 확장되고 있다. 이때 tagged pointer와 tagged metadata는 단순한 런타임 표현 최적화가 아니라, 객체 lifecycle과 ownership 정보를 컴파일러가 빠르게 읽기 위한 장치가 된다.

| 최적화 축 | 알고리즘 언어에서의 의미 |
|---|---|
| SCCP/branch pruning | 입력 조건이나 상수 조건으로 사라지는 경로를 제거하여 실행 경로를 단순화 |
| GVN/CSE | 반복 계산을 제거하여 같은 식을 여러 번 계산하지 않도록 함 |
| MemorySSA/Alias | 안전한 load forwarding과 dead store 제거로 메모리 접근 비용 감소 |
| Loop optimizer | trip count, LICM, strength reduction, bounds check 제거로 반복문 성능 개선 |
| Inlining/IPA | 작은 함수 호출 비용 제거, 함수 간 pure/read-only/escape summary 활용 |
| Escape/SROA | 힙 할당을 stack slot 또는 SSA 값으로 낮춰 공간 사용과 할당 비용 감소 |
| Number specialization | `number`가 값 범위에 따라 작은 정수, 큰 정수, 실수, 복소수 표현을 선택하도록 준비 |
| Allocator/lifecycle tag | 객체의 young/old, arena, borrowed, pinned, immortal 상태를 메모리 정책과 연결 |
| Source-aware JSON | 최적화 결과와 원본 코드를 연결하여 웹에서 설명 가능한 컴파일러를 구현 |

B++의 `number` 자료형도 알고리즘 최적화 언어라는 목표에서 중요하다. 알고리즘 문제를 풀 때 사용자는 `i32`, `i64`, `u64`, 큰 정수, 실수, 복소수 중 무엇을 선택해야 하는지 고민해야 한다. 잘못 선택하면 overflow가 발생하고, 반대로 항상 큰 정수만 사용하면 성능이 떨어진다. B++는 궁극적으로 사용자가 일반적인 정수와 수치 계산에서 `number`를 중심으로 코드를 작성하되, 컴파일러와 표준 라이브러리가 값 범위와 연산 성격에 따라 내부 표현을 최적화하는 방향을 지향한다. 작은 정수는 작은 storage로, 범위를 벗어나는 정수는 큰 정수 표현으로, 실수와 복소수는 해당 연산에 맞는 표현으로 다루는 방식이다. 이는 Python처럼 모든 숫자를 무겁게 다루자는 뜻이 아니라, 고수준 표현과 저수준 최적화를 동시에 얻기 위한 설계이다.

계약형 컴파일러에서 중요한 또 하나의 축은 "최적화 예산"이다. 컴파일러가 모든 가능한 특수화와 분석을 무제한으로 수행하면 생성 코드가 커지고 컴파일 시간이 폭증한다. 온라인 저지나 웹 컴파일러에서는 컴파일 시간도 사용자 경험의 일부이므로, 최적화 자체에도 budget이 필요하다. 예를 들어 loop unrolling은 작은 반복문에서는 유리하지만 큰 반복문에서는 code size를 폭발시킬 수 있다. 함수 specialization도 hot path에서는 효과적이지만 모든 호출 조합에 적용하면 컴파일러가 감당하기 어렵다. 따라서 B++ 컴파일러는 함수별, 루프별, pass별로 threshold와 budget을 두고, 예산을 넘는 최적화는 보류하거나 metadata로 이유를 남기는 방향을 취한다.

이러한 예산 기반 설계는 언어의 예측 가능성을 높인다. 사용자는 컴파일러가 어떤 최적화를 했는지, 하지 않았다면 왜 하지 않았는지 확인할 수 있어야 한다. 예를 들어 "이 루프는 code size budget 때문에 unroll하지 않음", "이 load는 alias proof가 부족해 hoist하지 않음", "이 allocation은 escape하므로 stack slot으로 낮추지 않음"과 같은 정보가 optimization report로 제공되면, 사용자는 코드를 어떻게 수정해야 하는지 알 수 있다. 이는 단순히 빠른 컴파일러를 만드는 것보다 더 교육적인 가치가 있다. B++는 알고리즘 풀이 플랫폼과 함께 제공되기 때문에, 최적화 실패 이유를 설명하는 기능은 학습 피드백으로도 활용될 수 있다.

컴파일러 계약형 모델은 온라인 저지와도 잘 결합된다. 기존 저지는 테스트 케이스를 통과하면 정답, 통과하지 못하면 오답 또는 시간 초과로 판단한다. 그러나 테스트는 모든 입력을 완전히 증명하지 못한다. Complexity contract가 도입되면 문제는 단순한 입출력 요구뿐 아니라 "이 문제는 `O(n log n)` 이하의 풀이를 요구한다"는 구조적 요구를 컴파일러와 공유할 수 있다. 물론 일반 프로그램의 정확한 시간복잡도를 완전히 자동 증명하는 것은 매우 어려운 문제이다. 따라서 B++의 접근은 모든 코드를 완전 증명하는 것이 아니라, 반복문, 표준 컨테이너, 표준 라이브러리, slice/Vec 길이, 재귀 구조처럼 알고리즘 풀이에서 자주 등장하는 패턴을 중심으로 보수적인 증명과 경고를 제공하는 것이다.

| 온라인 저지 관점 | 기존 방식 | B++ 계약형 방식 |
|---|---|---|
| 시간 제한 | 실행 후 시간 초과 판정 | 실행 전 loop/call 비용 후보 분석 및 최적화 report 제공 |
| 메모리 제한 | 실행 중 메모리 초과 판정 | allocation, container growth, temporary buffer 후보를 source range와 연결 |
| 오답 원인 | 출력 불일치 표시 | 컴파일러 산출물과 source map을 통해 내부 변환 과정 확인 |
| 학습 피드백 | 정답/오답 중심 | 복잡도, 메모리, 최적화 실패 이유까지 설명 가능 |
| 문제 요구사항 | 자연어 설명 중심 | 향후 complexity contract와 채점 정책 연결 가능 |

현재 구현된 웹 컴파일러의 source-aware JSON은 이러한 방향의 기반이다. `--emit-json --views ast,ir,ssa,asm` 형태의 출력은 AST, SSA, ASM을 한 번에 구조화하여 제공하고, 각 단계의 source range와 generated 여부를 포함한다. 프론트엔드는 더 이상 문자열 검색으로 ASM 라인을 추정할 필요가 없고, 선택 범위와 source range의 겹침을 기준으로 안정적으로 표시할 수 있다. 이 구조는 향후 complexity report에도 그대로 확장될 수 있다. 예를 들어 특정 loop가 `O(n)`으로 추론되었다면 해당 loop의 AST node id와 SSA block id, source range를 report에 포함하여 웹 UI가 원본 코드 위치를 직접 표시할 수 있다.

source-aware JSON은 단순한 화면 하이라이트 기능을 위한 부속물이 아니라, B++ 컴파일러 연구의 공통 데이터 형식이다. AST JSON은 문법 분석 결과를 검증하는 데 쓰이고, IR/SSA JSON은 최적화 pass가 원본 코드를 어떻게 바꾸었는지 추적하는 데 쓰이며, ASM JSON은 최종 코드 생성 결과를 SSA instruction과 연결하는 데 쓰인다. 여기에 complexity report와 optimization report가 같은 `rangeId`, `astNodeId`, `ssaInstructionId`를 공유하면, 웹 IDE는 "이 코드가 왜 느릴 수 있는가", "이 최적화는 왜 적용되지 않았는가", "이 할당은 왜 힙에 남았는가"를 단계별로 보여줄 수 있다.

| JSON view | 포함해야 하는 핵심 정보 | 활용 |
|---|---|---|
| AST | node id, kind, span, child list, identifier/literal/type span | 문법 구조 시각화, source 선택과 AST 노드 연결 |
| IR | instruction id, opcode, operands, sourceRanges, astNodeIds | lowering 결과 검증, 고수준 연산과 중간 표현 연결 |
| SSA | block id, instruction id, use-def, phi, sourceRanges, generated flag | 최적화 전후 값 흐름 추적, loop/alias/escape 분석 근거 |
| ASM | line text, instruction, operands, sourceRanges, segments, SSA/IR links | Godbolt식 소스-어셈블리 대응, operand 단위 hover와 highlight |
| Report | complexity budget, inferred cost, optimization decision, evidence | 시간·공간 budget 경고와 최적화 실패 이유 설명 |

결국 B++ 컴파일러의 목표는 "빠른 코드를 생성하는 컴파일러"에만 머무르지 않는다. 목표는 사용자가 알고리즘을 더 안전하고 예측 가능하게 작성하도록 돕는 언어와 컴파일러를 만드는 것이다. 사용자는 고수준 문법과 `number` 같은 편리한 타입을 사용하면서도, 컴파일러는 내부에서 값 범위, 메모리 상태, 반복문 구조, alias 관계, 함수 호출 비용을 분석한다. 그리고 그 결과를 AST/SSA/IR/ASM/source map/optimization report로 다시 사용자에게 돌려준다. 이러한 구조가 완성되면 B++는 단순한 교육용 언어를 넘어, 알고리즘 학습과 성능 분석을 동시에 지원하는 계약형 알고리즘 언어로 발전할 수 있다.

#### 그림 2. 컴파일 성공 후 AST 시각화

![그림 2. 컴파일 성공 후 AST 시각화](report-assets/02-ide-compile-ast.png)

그림 2는 사용자가 컴파일 버튼을 눌러 B++ 코드가 성공적으로 컴파일된 뒤의 화면이다. 하단 콘솔에는 컴파일 성공 메시지가 표시되고, 오른쪽 패널에는 AST 그래프가 출력된다. AST는 프로그램의 문법 구조를 노드와 엣지로 표현하므로, 사용자는 코드가 컴파일러 내부에서 어떤 계층 구조로 해석되는지 확인할 수 있다. 예를 들어 함수 정의, import 문, 블록, 호출식, 리터럴 같은 요소가 각각의 노드로 나뉘어 표시되면, 학습자는 문법 분석 단계의 결과를 직접 볼 수 있다.

이 기능은 컴파일러 수업이나 언어 구현 학습에서 특히 중요하다. 기존 온라인 컴파일러는 실행 결과만 보여주기 때문에 사용자는 컴파일러가 내부적으로 어떤 구조를 만들었는지 알기 어렵다. 반면 본 작품은 컴파일러의 중간 단계를 시각적으로 드러내어 학습자가 프로그램 구조를 분석할 수 있게 한다. AST 그래프는 단순한 장식 요소가 아니라, 문법 오류를 이해하거나 언어 기능을 구현할 때 내부 표현을 검증하는 실험 도구로 사용될 수 있다.

#### 그림 3. ASM 출력 및 소스맵 기반 분석 패널

![그림 3. ASM 출력 및 소스맵 기반 분석 패널](report-assets/03-ide-asm-source-map.png)

그림 3은 ASM 탭의 화면이다. ASM 패널은 B++ 코드가 최종적으로 어떤 어셈블리 명령으로 내려가는지 보여준다. 컴파일러는 JSON source map을 통해 각 ASM line에 대응되는 source range를 제공하고, 프론트엔드는 이를 이용해 소스 코드 선택 범위와 출력 라인을 연결한다. 이때 소스맵은 단순히 라인 번호만 제공하는 것이 아니라 byte offset, stable range id, 관련 SSA instruction id, generated 여부, generatedReason 같은 정보를 포함하도록 설계되었다. 이러한 정보는 프론트엔드가 실제 사용자 선택 범위와 컴파일 산출물의 관계를 더 엄격하게 판정하는 기반이 된다.

이 구조는 단순 문자열 검색 방식보다 오탐 가능성이 낮다. 예를 들어 동일한 변수명이나 동일한 코드 조각이 여러 번 등장하더라도, source range와 offset 정보를 사용하면 원본 코드의 어느 범위에서 생성된 결과인지 더 구체적으로 판단할 수 있다. 물론 컴파일러가 하나의 소스 구문을 여러 어셈블리 명령으로 내릴 수 있고, 최적화 과정에서 한 명령이 여러 소스 범위와 관련될 수 있기 때문에 완전히 일대일 대응이 되는 것은 아니다. 그러나 source map을 기반으로 한 방식은 교육용 시각화에서 충분히 설명 가능한 근거를 제공한다.

#### 그림 4. 터미널 실행 결과

![그림 4. 터미널 실행 결과](report-assets/04-terminal-run-result.png)

그림 4는 컴파일 후 실행 결과가 터미널에 출력된 화면이다. 예제 프로그램은 84의 소인수 분해 결과를 출력한다. 터미널은 단순 stdout 표시뿐 아니라 stdin 입력이 필요한 프로그램도 처리할 수 있도록 WebSocket 기반으로 연결된다. 실행 전에는 프로그램을 컴파일하고, 실행 중에는 표준 입력을 전달하며, 실행 후에는 종료 코드와 stdout/stderr를 구분하여 표시한다.

터미널 기능은 온라인 IDE의 사용성을 높이는 핵심 요소이다. 사용자는 실행 버튼만으로 컴파일과 실행을 이어서 수행할 수 있고, 프로그램 종료 코드와 표준 출력 결과를 한눈에 확인할 수 있다. 또한 알고리즘 문제 풀이에서는 입력을 바꿔가며 실행하는 경우가 많기 때문에, 터미널과 출력 콘솔을 분리한 구조는 반복 실험에 필요한 흐름을 제공한다. 본 작품은 단순히 정답 제출만을 제공하는 것이 아니라, 사용자가 코드의 동작을 직접 관찰하고 수정하는 개발 흐름을 지원한다.

## 5. 연구 방법 및 제작 과정

### 5.1 디자인 및 계획 단계

초기 설계 단계에서는 서비스의 목적을 "컴파일러 학습을 위한 웹 기반 실행·분석 환경"으로 정의하였다. 이 정의는 이후 화면 구성과 기능 우선순위를 결정하는 기준이 되었다. 만약 목표가 일반적인 온라인 저지였다면 문제 목록과 채점 결과가 가장 중요한 화면이 되었을 것이다. 반대로 일반적인 온라인 컴파일러였다면 코드 편집기와 실행 결과만으로 충분했을 수 있다. 그러나 본 작품은 컴파일러 학습을 핵심 가치로 삼았기 때문에, 코드 편집 영역과 컴파일러 산출물 분석 패널이 동시에 보여야 했고, 문제 풀이 화면에서도 사용자가 자신의 코드와 채점 결과를 한 화면 흐름 안에서 오갈 수 있어야 했다.

계획 단계에서 화면은 메인 IDE, 컴파일러 산출물 시각화 패널, 문제 목록, 문제 상세, 문제 풀이와 채점 패널, 제출 이력, 리더보드, 컴파일 큐 조회 화면, 커뮤니티 화면, 로그인과 회원가입 및 비밀번호 재설정 화면으로 나누어 설계하였다. 여기서 중요한 점은 각 화면이 독립적으로 존재하는 것이 아니라 하나의 학습 흐름으로 이어져야 한다는 것이다. 사용자는 먼저 문제 목록에서 자신에게 맞는 문제를 찾고, 문제 상세에서 요구사항을 읽고, IDE에서 코드를 작성하고, 예제 채점으로 기본 동작을 확인하고, 전체 채점으로 최종 결과를 제출한다. 이후 제출 이력과 리더보드에서 결과를 확인하고, 막히는 부분은 커뮤니티에서 질문할 수 있다. 이 흐름이 끊기지 않도록 라우팅과 버튼 배치, 상태 저장 방식을 설계하였다.

UI 설계에서는 작업형 도구에 맞게 과도한 장식보다 정보 밀도와 반복 사용성을 우선하였다. IDE 화면은 좌우 및 상하 분할 패널 구조를 사용하여 코드, 출력, 그래프를 동시에 확인할 수 있게 하였다. 문제 목록은 필터 사이드바와 표 형태의 리스트를 사용하여 문제 수가 늘어나도 검색과 정렬이 가능하도록 하였다. 커뮤니티는 공지, 문제, 자유 탭으로 나누어 사용자가 글의 목적에 따라 게시판을 선택할 수 있게 했고, 문제별 게시판에서는 특정 문제와 게시글을 연결할 수 있도록 하였다. 이러한 디자인 방향은 "예쁘게 보이는 첫 화면"보다 "반복적으로 사용해도 피로하지 않은 도구"에 가깝다.

#### 그림 5. 문제 목록과 필터 화면

![그림 5. 문제 목록과 필터 화면](report-assets/05-problem-list-filter.png)

그림 5는 문제 목록 화면이다. 왼쪽에는 검색, 난이도 범위, 태그, 정렬 조건이 배치되어 있고, 오른쪽에는 문제 목록이 표 형태로 표시된다. 각 문제는 난이도, 풀이 상태, 제목, 요약, 태그, 문제 풀기 버튼을 포함한다. 단순히 문제 제목만 나열하는 방식이라면 문제 수가 적을 때는 충분해 보일 수 있지만, 문제가 20개를 넘고 이후 더 늘어나는 상황에서는 검색과 필터가 없으면 사용자가 원하는 문제를 찾기 어렵다. 따라서 초기 단계부터 문제 수 증가를 고려하여 목록 화면을 설계하였다.

### 5.2 구현 및 제작 단계

구현은 프론트엔드, 백엔드, 샌드박스, 데이터베이스, 배포 자동화로 나누어 진행하였다. 프론트엔드에서는 React와 TypeScript를 사용하여 화면을 구성하였다. TypeScript를 사용한 이유는 API 응답 구조와 UI 상태가 복잡해질수록 타입 안정성이 중요해지기 때문이다. 컴파일 결과는 단순 문자열이 아니라 성공 여부, 오류 정보, AST, SSA, IR, ASM, source map, 실행 출력, 시간 정보 등 여러 필드를 포함한다. 이러한 데이터를 명확하게 타입으로 정의하면 컴포넌트 사이에서 잘못된 데이터 구조가 전달되는 문제를 줄일 수 있다.

Monaco Editor는 코드 작성 영역에 사용하였다. 사용자는 메인 IDE와 문제 풀이 화면에서 코드를 편집하며, 선택 범위는 컴파일러 산출물 하이라이트와 연결된다. Zustand는 코드, 실행 상태, 컴파일 결과, 터미널 상태, 테마, 자동 저장 상태를 관리하는 전역 store로 사용하였다. 컴파일러 시각화에는 AST와 SSA 그래프를 위한 React Flow와 Dagre 기반 자동 배치를 적용하였다. 그래프 뷰어는 노드 수가 늘어나도 기본적인 탐색이 가능하도록 확대, 축소, 이동, 자동 배치가 가능한 구조로 구현하였다.

백엔드에서는 FastAPI 기반 API 서버를 구현하였다. 주요 라우터는 컴파일/실행, 문제, 제출, 커뮤니티, 인증, 큐와 운영성 조회 기능으로 분리하였다. FastAPI는 Pydantic 기반 요청 검증과 자동 문서화가 강점이기 때문에, 다양한 API가 필요한 본 프로젝트에 적합하였다. SQLAlchemy 모델은 사용자, 문제, 테스트 케이스, 제출, 점수, 게시글, 댓글, 저장 코드, 큐 작업 기록을 표현한다. 문제 제출 시에는 제출 기록이 생성되고, 예제 또는 전체 채점 결과가 케이스별로 계산된 뒤, 최종 판정과 획득 점수가 저장된다.

샌드박스는 Docker 컨테이너 기반으로 구성하였다. 사용자 코드는 임시 디렉터리에 저장된 뒤 컨테이너 내부에서 컴파일 또는 실행된다. 컨테이너 실행 시 네트워크 비활성화, read-only 파일 시스템, 메모리 제한, CPU 제한, PID 제한, capability 제거, no-new-privileges 옵션을 적용하였다. 이는 사용자 코드 실행이 서버 전체에 영향을 주지 않도록 하기 위한 핵심 보안 장치이다. 또한 실행 결과는 제한 시간과 출력 크기 제한을 고려하여 수집하며, 판정은 정답, 오답, 컴파일 실패, 런타임 오류, 시간 초과, 메모리 초과 같은 상태로 정리된다.

B++ 컴파일러 구현은 별도의 서비스 기능이 아니라 본 작품의 핵심 구현 대상이다. Parser 단계에서는 source span과 AST node id를 보존하고, lowering 단계에서는 `print`, `println`, `input`, string literal, `number`, method call처럼 내부 helper 호출로 바뀌는 구문이 원래 source origin을 잃지 않도록 설계하였다. SSA 단계에서는 instruction과 block이 source range, generated 여부, stable id를 유지하도록 하였고, 최적화 pass는 instruction이 사라지거나 합쳐질 때 여러 origin을 보존할 수 있는 방향으로 metadata를 연결하였다. Backend와 ASM 출력은 최종 line을 SSA/IR instruction id와 연결하여 웹 IDE가 문자열 검색이 아닌 source range overlap으로 하이라이트할 수 있게 하였다.

최적화 구현은 O1/O2 pass를 중심으로 진행하였다. 상수 전파, branch pruning, GVN/CSE, copy propagation, MemorySSA 기반 load/store 정리, loop metadata 분석, escape analysis, stack lowering, tagged lifecycle metadata, allocator policy 연결이 주요 축이다. 이 과정에서 단순히 pass를 추가하는 데 그치지 않고, 각 pass가 어떤 source range와 관련되는지, 어떤 조건 때문에 최적화를 적용했거나 적용하지 않았는지 report할 수 있는 구조를 마련하였다. 특히 알고리즘 풀이에서 반복문과 메모리 할당이 병목이 되기 쉽기 때문에, loop trip count, bounds proof, container growth, allocation site를 추적하는 metadata를 중요하게 다루었다.

컴파일러 산출물 검증은 작은 golden test를 중심으로 접근하였다. 예를 들어 `print`와 `println` lowering이 잘못되면 출력 자체가 깨지고, source map이 부정확하면 웹 IDE에서 전혀 관련 없는 ASM line이 칠해질 수 있다. 따라서 출력 함수, loop, branch, array/slice 접근, number 연산, tagged metadata, regalloc, SSA 최적화에 대해 성공 runtime test와 source map test를 묶어 회귀를 확인하였다. 테스트 파일은 너무 잘게 쪼개면 CI 컴파일 횟수가 늘어나므로, 최종 테스트는 성향이 비슷한 케이스끼리 bundle로 묶어 실행 비용을 줄이는 방향으로 정리하였다.

배포는 Docker Compose와 Nginx를 사용하였다. 서버에서는 `/webcompiler/` 경로를 통해 프론트엔드를 제공하고, `/webcompiler/api/` 경로는 백엔드 API로 프록시한다. GitHub Actions는 CI 성공 후 원격 서버에서 배포 스크립트를 실행하도록 구성하였다. 배포 과정에서는 B++ 컴파일러와 표준 라이브러리를 런타임 이미지 안에서 함께 사용할 수 있도록 경로를 정리하였다. 이전에는 릴리즈 패키지와 샌드박스 내부 경로가 맞지 않아 표준 라이브러리를 찾지 못하는 문제가 있었지만, 컴파일러 바이너리, 표준 라이브러리, 실행 wrapper를 한 배포 단위로 묶는 방식으로 서버 환경에서도 안정적으로 동작하도록 개선하였다.

#### 그림 6. 문제 상세 화면

![그림 6. 문제 상세 화면](report-assets/06-problem-detail.png)

그림 6은 `Hello, World!` 문제의 상세 화면이다. 문제 난이도, 태그, 배점, 풀이 상태, 문제 설명, 입력 형식, 출력 형식, 예제 입출력, 최근 제출 이력을 한 화면에서 확인할 수 있다. 상단에는 큐 화면으로 이동하는 버튼과 문제 풀이 버튼이 있어, 사용자는 문제를 읽은 뒤 곧바로 풀이 화면으로 이동할 수 있다. 문제 상세 화면은 온라인 저지의 중심 화면이며, 문제 요구사항을 정확히 이해하게 하는 역할을 한다.

이 화면에서 중요한 점은 문제 설명과 제출 흐름이 분리되지 않는다는 것이다. 사용자는 문제 설명을 읽은 뒤 다른 페이지를 새로 검색하거나 로컬 편집기를 열 필요 없이 바로 문제 풀이 화면으로 이동한다. 또한 최근 제출 이력이 함께 보이기 때문에, 해당 문제에 대해 자신이나 다른 사용자가 어떤 판정을 받았는지 확인할 수 있다. 교육용 서비스에서는 사용자가 문제를 단번에 맞히지 못하는 경우가 많으므로, 이전 제출 결과와 문제 설명을 같은 흐름 안에서 확인할 수 있는 구조가 학습 반복에 도움이 된다.

#### 그림 7. 문제 풀이 및 채점 결과

![그림 7. 문제 풀이 및 채점 결과](report-assets/07-judge-accepted.png)

그림 7은 문제 풀이 화면에서 채점을 수행한 결과이다. 왼쪽에는 문제 설명과 채점 패널이 있고, 가운데에는 문제별로 저장된 코드가 표시된다. 사용자는 코드를 작성한 뒤 예제 채점으로 공개 예제 기준의 결과를 먼저 확인하고, 전체 채점으로 최종 결과를 제출할 수 있다. 채점 패널은 판정 결과를 정답, 오답, 컴파일 실패, 런타임 오류, 시간 초과, 메모리 초과 등으로 구분하여 보여준다.

예제 채점과 전체 채점을 분리한 이유는 온라인 저지의 정보 노출 문제를 줄이기 위해서이다. 사용자가 "숨김 테스트 몇 개 중 몇 개 통과"와 같은 정보를 그대로 보게 되면, 내부 테스트 구성이나 케이스 수가 불필요하게 드러난다. 따라서 본 작품에서는 공개 예제를 기준으로 한 "예제 채점"과 전체 케이스를 기준으로 한 "채점"이라는 용어를 사용하였다. 이 표현은 사용자가 결과의 의미를 이해하는 데 충분하면서도 내부 테스트 구조를 직접 노출하지 않는다.

### 5.3 테스트 및 개선 단계

테스트는 단위 테스트, API 테스트, E2E 테스트, 수동 배포 검증을 병행하였다. 백엔드에서는 컴파일 서비스, 문제 제출, 리더보드, 제품 기능을 대상으로 pytest 테스트를 작성하였다. 예를 들어 문제 제출 기능은 정상 코드가 정답으로 판정되는지, 잘못된 출력이 오답으로 처리되는지, 컴파일 오류가 컴파일 실패로 저장되는지, 제출 점수가 사용자 점수에 반영되는지를 확인해야 한다. 프론트엔드에서는 라우팅, compiler store, 그래프 뷰어 컴포넌트에 대해 Vitest 테스트를 수행하였다. 상태 관리 로직은 UI에서 직접 보이지 않지만, 자동 저장이나 컴파일 결과 표시처럼 사용자 경험에 큰 영향을 주므로 별도 검증이 필요했다.

E2E 테스트는 Playwright를 사용하여 실제 브라우저에서 수행하였다. 단순히 함수 단위로 성공하는 것만으로는 서비스가 실제 사용 가능한지 판단하기 어렵기 때문이다. `/webcompiler/` 경로 접근, 코드 입력, 컴파일 버튼 클릭, 실행 결과 확인, 리더보드 표시, 터미널 입출력, 문제 제출, 커뮤니티 게시글 작성과 같은 흐름을 실제 Chrome에서 검증하였다. 특히 본 보고서에 포함된 스크린샷도 공개 배포 주소에서 직접 캡처하였으므로, 문서에 들어간 화면은 로컬 목업이 아니라 서버에 올라간 결과를 기준으로 한다.

개선 과정에서는 여러 문제가 발견되었다. 서버에서 B++ std root를 찾지 못해 `Could not determine std root` 오류가 발생한 문제는 컴파일러 패키지와 샌드박스 내부 경로가 맞지 않아 생긴 것이었다. 이를 해결하기 위해 컴파일러 바이너리, 표준 라이브러리, 실행 wrapper를 같은 배포 단위로 묶고, 샌드박스 내부에서 표준 라이브러리 경로를 안정적으로 찾도록 수정하였다. 데이터베이스가 초기화되는 문제는 컨테이너별 데이터베이스가 분리되거나 volume 구성이 일관되지 않아 발생했으며, 공유 PostgreSQL 네트워크와 volume 기반 데이터 보존 구조로 변경하여 재배포 후에도 데이터가 유지되도록 하였다.

UI 측면에서도 개선이 있었다. 숨김 테스트 개수를 노출하는 문구는 온라인 저지의 내부 구조를 사용자에게 불필요하게 보여주는 문제였으므로 "예제 채점"과 "채점"으로 용어를 정리하였다. 커뮤니티 게시글의 Markdown 서식 문제는 ReactMarkdown, remark-math, rehype-katex를 적용하여 해결하였다. 소스맵 하이라이트는 처음에는 문자열 검색 또는 넓은 범위 추정 방식에 가까웠기 때문에 동일한 코드 조각이 여러 위치에 등장할 때 부정확하게 표시되는 문제가 있었다. 이후 컴파일러가 JSON source map을 직접 제공하고, 프론트엔드가 source range와 offset을 기준으로 선택 범위와의 겹침을 판단하도록 변경하였다. 배포 중 SSH 연결이 끊기는 문제는 서버 빌드 중 장시간 출력이 없어 발생할 수 있었으므로 GitHub Actions SSH keepalive 옵션을 추가하여 안정성을 높였다.

| 문제 | 원인 | 해결 |
|---|---|---|
| 서버에서 B++ std root를 찾지 못함 | 컴파일러 패키지와 샌드박스 경로 불일치 | 컴파일러 바이너리, 표준 라이브러리, 실행 wrapper를 같은 배포 단위로 정리 |
| DB 초기화 문제 | 컨테이너별 DB가 분리되어 상태가 유지되지 않음 | 공유 PostgreSQL 네트워크와 volume 기반 데이터 보존 구조로 변경 |
| 숨김 테스트 개수 노출 | UI 문구가 내부 테스트 구조를 드러냄 | `예제 채점`, `채점` 두 단계로 용어 정리 |
| 커뮤니티 Markdown 서식 문제 | 게시글 렌더링이 일반 텍스트 중심 | ReactMarkdown, remark-math, rehype-katex 적용 |
| 소스맵 하이라이트 부정확 | 문자열 검색 기반 매핑 | 컴파일러 JSON source map의 range/offset 기반 매핑으로 변경 |
| 배포 중 SSH 끊김 | 서버 빌드 중 장시간 출력이 없어 연결 종료 | GitHub Actions SSH keepalive 옵션 추가 |

위 표는 주요 문제를 요약한 것이지만, 실제 개선 과정에서 중요한 점은 문제를 단순히 임시로 우회하지 않고 운영 구조에 맞게 정리했다는 것이다. 예를 들어 std root 문제는 컨테이너 안에서 환경 변수만 임시로 지정하는 방식으로도 일부 해결할 수 있었지만, 컴파일러와 표준 라이브러리 배치가 재현 가능해야 서버 재배포 시 같은 문제가 반복되지 않는다. 데이터베이스 문제 역시 한 번 데이터를 다시 넣는 것으로는 해결되지 않으며, 컨테이너 갱신과 데이터 보존 경로가 명확해야 한다. 이러한 개선을 통해 작품은 데모 실행 가능 상태에서 실제 배포 운영 가능 상태에 가까워졌다.

#### 그림 8. 제출 이력 화면

![그림 8. 제출 이력 화면](report-assets/08-submissions-history.png)

그림 8은 제출 이력 화면이다. 이 화면은 전체 제출 수, 필터링된 제출 수, 문제 ID, 사용자명, 판정, 상태, 내 제출 여부를 기준으로 결과를 필터링할 수 있다. 표에는 제출 문제, 사용자, 언어, 상태, 판정, 예제 채점, 획득 점수, 제출 시간이 표시된다. 온라인 저지에서 제출 이력은 단순 기록 이상의 의미를 가진다. 사용자는 어떤 문제에서 어떤 오류가 반복되었는지 확인할 수 있고, 운영자는 특정 문제에서 컴파일 실패나 시간 초과가 과도하게 발생하는지 파악할 수 있다.

제출 이력은 문제 풀이의 반복성을 지원한다. 사용자는 처음 제출에서 컴파일 실패를 받았을 수 있고, 다음 제출에서는 오답을 받았으며, 최종 제출에서 정답을 받을 수 있다. 이러한 과정이 기록으로 남아야 학습자는 자신의 진행 과정을 되돌아볼 수 있다. 또한 문제별 필터와 사용자별 필터가 있어야 데이터가 많아진 뒤에도 특정 제출을 찾을 수 있다. 따라서 제출 이력 화면은 단순한 부가 기능이 아니라 온라인 저지 서비스의 핵심 기록 장치이다.

#### 그림 9. 컴파일 큐 조회 화면

![그림 9. 컴파일 큐 조회 화면](report-assets/09-compile-queue.png)

그림 9는 컴파일 큐 화면이다. 이 화면은 컴파일, 실행, 채점 작업을 통합적으로 보여준다. 상단 필터를 통해 작업 종류, 상태, 판정을 좁힐 수 있고, 문제별 집계와 사용자별 집계도 함께 제공된다. 초기에는 큐가 없거나 표시할 작업이 없을 때 충분한 정보를 제공하지 못하는 문제가 있었지만, 이후 작업 기록을 저장하고 사용자가 직접 조회할 수 있도록 개선하였다. 또한 관리자만 볼 수 있는 기능으로 제한하지 않고 모든 사용자가 문제별, 사용자별 큐 현황을 볼 수 있게 하였다.

이 기능은 사용자가 많아질 때 특히 중요하다. 단순히 "현재 작업 없음"만 표시하는 것은 작업이 적을 때는 문제가 없어 보일 수 있지만, 사용자가 늘어나면 어떤 작업이 지연되고 있는지, 어떤 문제에서 실패가 반복되는지, 어떤 사용자의 요청이 많은지 확인하기 어렵다. 컴파일 큐 화면은 `정답`, `오답`, `컴파일 실패`, `런타임 오류`, `시간 초과`, `메모리 초과`와 같은 판정을 명시적으로 보여준다. 따라서 사용자는 자신의 작업이 어떤 결과로 끝났는지 이해할 수 있고, 운영자는 시스템 병목이나 문제 데이터 오류를 더 빨리 파악할 수 있다.

기능 구현 결과, 본 작품은 웹 기반 코드 작성, 컴파일, 실행, 분석, 문제 풀이, 제출 기록, 커뮤니티, 배포 운영까지 하나의 서비스로 연결하는 데 성공하였다. 코드 작성 영역에서는 Monaco Editor 기반 편집기, 파일명 표시, 복사, 자동 저장을 제공한다. 컴파일 영역에서는 B++ 컴파일 성공과 실패 메시지를 구분하고, 오류가 발생하면 line과 column 정보를 사용자에게 전달한다. 실행 영역에서는 일반 HTTP 실행과 WebSocket 기반 터미널 실행을 모두 지원하여, 단순 출력 프로그램과 대화형 입력 프로그램을 모두 다룰 수 있다.

### 6.2 B++ 레이팅 산정 방식

B++ 레이팅은 사용자가 해결한 문제의 난이도와 해결 문제 수를 함께 반영하는 학습 성취 지표이다. 기존 XP는 문제에 부여된 점수를 누적하는 방식이므로 운영자가 문제별 배점을 어떻게 설정했는지에 영향을 많이 받는다. 반면 레이팅은 문제 난이도 순서와 해결한 문제 수를 기준으로 산정하므로, 사용자가 더 어려운 문제를 해결했는지와 꾸준히 여러 문제를 해결했는지를 동시에 보여준다. 따라서 리더보드의 대표 순위는 XP가 아니라 B++ 레이팅을 기준으로 정렬하였다.

레이팅 산식은 다음과 같다. 먼저 사용자가 정답으로 통과한 고유 문제만 계산 대상으로 삼는다. 동일한 문제를 여러 번 제출하더라도 최초 해결 기록만 인정하며, 익명 제출은 사용자 계정에 연결되지 않으므로 레이팅에 반영하지 않는다. 삭제된 문제나 실제 문제 테이블에 존재하지 않는 수동 점수 기록도 계산에서 제외한다. 각 문제의 난이도 값은 현재 서비스의 난이도 순서를 그대로 사용하며, `iron5`를 1점, `diamond1`을 30점으로 둔다. 그 뒤 해결한 문제 중 난이도 값이 높은 상위 100개를 더하고, 해결 문제 수에 따른 보너스를 더한다.

```text
B++ Rating =
  sum(top 100 difficulty values among unique accepted problem_ids)
  + round_half_up(200 * (1 - 0.997 ^ accepted_count))
```

이 산식에서 첫 번째 항은 어려운 문제를 해결한 정도를 나타낸다. 단순히 문제를 많이 푸는 것만으로 높은 레이팅을 얻는 것이 아니라, 난이도가 높은 문제를 해결할수록 더 큰 값이 반영된다. 두 번째 항은 꾸준히 문제를 해결한 정도를 나타낸다. 해결 수 보너스는 최대 200점에 수렴하도록 설계하여, 문제 수가 많아질수록 보너스가 무한히 커지지 않게 하였다. 이 구조는 레이팅이 문제 난이도 중심으로 형성되면서도 꾸준한 학습을 일정 부분 보상하도록 한다.

티어는 레이팅 구간에 따라 `Unrated`, `Iron`, `Bronze`, `Silver`, `Gold`, `Platinum`, `Diamond`, `Master`로 구분하였다. 예를 들어 30점 이상은 `Iron V`, 200점 이상은 `Bronze V`, 800점 이상은 `Silver V`, 1600점 이상은 `Gold V`, 2200점 이상은 `Platinum V`, 2700점 이상은 `Diamond V`, 3000점 이상은 `Master`로 표시된다. 이 티어는 사용자가 자신의 현재 위치를 숫자만이 아니라 단계로도 이해할 수 있게 하는 장치이다.

구현에서는 레이팅을 별도 DB 컬럼으로 저장하지 않고 요청 시 계산하는 파생값으로 두었다. 이 방식은 문제 난이도를 수정했을 때 과거 사용자 레이팅을 따로 마이그레이션하지 않아도 최신 난이도 기준으로 즉시 반영된다는 장점이 있다. 백엔드는 `UserProblemScore`와 `Problem`을 조인하여 실제 존재하는 문제의 해결 기록만 가져오고, 사용자별 레이팅 통계를 계산한 뒤 리더보드 응답과 사용자 프로필 응답에 포함한다. 프론트엔드는 리더보드에서 순위, 사용자, 티어, 레이팅, 해결 수, XP를 함께 표시하고, 프로필 모달에서도 동일한 통계를 읽기 전용으로 보여준다.

### 6.3 성능 최적화 및 확장 구조

서비스가 단일 사용자 실험 수준을 넘어 여러 사용자가 동시에 컴파일, 실행, 채점을 수행하는 환경으로 확장되면 병목은 크게 세 영역에서 발생한다. 첫째는 제출 이력, 컴파일 큐, 리더보드 조회처럼 반복적으로 읽히는 데이터베이스 쿼리이다. 둘째는 사용자 코드 실행처럼 CPU와 컨테이너 생성 비용이 큰 작업의 큐 처리이다. 셋째는 백엔드 인스턴스를 여러 개로 늘렸을 때 각 인스턴스의 메모리 상태가 서로 분리되는 문제이다. 본 작품은 이러한 병목을 줄이기 위해 데이터베이스 인덱스, 커넥션 풀, PgBouncer, Redis 기반 캐시와 전역 큐 조정, Nginx upstream 기반 로드밸런싱 구조를 추가하였다.

데이터베이스 계층에서는 자주 사용되는 조회 조건을 기준으로 인덱스를 보강하였다. 제출 이력은 문제별, 사용자별, 판정별로 필터링되고 최신순으로 정렬되므로 `submissions(problem_id, created_at)`, `submissions(user_id, created_at)`, `submissions(verdict, created_at)` 인덱스를 추가하였다. 컴파일 큐는 상태, 판정, 문제, 사용자 기준으로 조회되므로 `compile_queue_jobs(status, queued_at)`, `compile_queue_jobs(verdict, queued_at)`, `compile_queue_jobs(problem_id, queued_at)`, `compile_queue_jobs(user_id, queued_at)` 인덱스를 추가하였다. 커뮤니티 게시글은 문제별 최신 글 조회가 중심이므로 `comments(problem_id, created_at)` 인덱스를 추가하였고, 문제 목록은 난이도 기반 필터링과 생성순 정렬을 고려해 `problems(difficulty, created_at)` 인덱스를 추가하였다. 또한 SQLAlchemy 엔진에 `pool_pre_ping`, `pool_size`, `max_overflow`, `pool_recycle` 설정을 적용하여 DB 연결 재사용과 오래된 연결 회수를 명시적으로 관리하도록 하였다.

PostgreSQL 앞에는 PgBouncer를 둘 수 있도록 Docker Compose 구성을 확장하였다. PgBouncer는 백엔드 인스턴스가 늘어날 때 PostgreSQL에 직접 연결되는 클라이언트 수가 급격히 증가하는 문제를 완화한다. 본 작품의 PgBouncer 설정은 transaction pooling 방식을 사용하므로, 짧은 API 요청과 큐 조회처럼 트랜잭션 단위로 DB를 사용하는 FastAPI 서비스에 적합하다. 백엔드는 기본적으로 PgBouncer를 통해 PostgreSQL에 연결하며, 필요한 경우 환경 변수로 직접 PostgreSQL 연결 문자열을 지정할 수 있도록 하였다.

Redis는 두 가지 용도로 사용한다. 첫 번째 용도는 레이팅과 리더보드 캐시이다. B++ 레이팅은 문제 해결 기록과 문제 난이도를 조인해 계산하므로 사용자가 많아질수록 리더보드 조회 비용이 커질 수 있다. Redis가 설정되어 있으면 사용자별 레이팅 통계와 상위 리더보드 응답을 짧은 TTL로 캐시하고, 정답 처리, 수동 점수 반영, 문제 생성·수정·삭제 시 관련 캐시를 무효화한다. 이를 통해 반복적인 리더보드 조회는 Redis에서 빠르게 응답하고, 데이터가 변경된 경우에는 최신 DB 기준으로 다시 계산하도록 하였다.

두 번째 용도는 컴파일 큐의 전역 조정이다. 기존 큐는 백엔드 프로세스 내부의 `asyncio.Condition`을 사용했기 때문에 단일 인스턴스에서는 정상적으로 동작하지만, 백엔드를 여러 개 띄우면 인스턴스마다 별도의 큐가 생기는 문제가 있었다. 개선된 구조에서는 Redis가 사용 가능할 때 대기열, 실행 중 작업 집합, active count, 작업 heartbeat를 Redis에 저장한다. 각 백엔드 인스턴스는 Redis의 FIFO 대기열을 기준으로 자신의 차례와 전역 동시 실행 제한을 확인한 뒤 컴파일 또는 채점 작업을 실행한다. 작업자가 비정상 종료되어 heartbeat가 만료되면 큐 조회 시 해당 작업을 실패 상태로 복구하고 active count를 다시 맞춘다. Redis가 없는 개발 환경에서는 기존 in-memory 큐가 그대로 사용되므로 로컬 개발 편의성도 유지된다.

로드밸런싱은 프론트엔드 Nginx 설정에 backend upstream을 두는 방식으로 적용하였다. Nginx는 API, health check, WebSocket 터미널 요청을 backend upstream으로 전달하며, upstream은 `least_conn`과 keepalive를 사용한다. 이를 통해 Docker Compose 또는 배포 환경에서 백엔드 인스턴스를 여러 개로 늘렸을 때 API 요청을 분산할 수 있다. WebSocket 터미널은 연결 유지 시간이 길기 때문에 일반 HTTP 요청보다 로드밸런싱 영향이 크며, Redis 큐와 DB 기반 상태 기록을 함께 사용하면 백엔드 인스턴스가 늘어나도 컴파일 큐와 제출 기록의 일관성을 유지할 수 있다.

인증 요청 제한도 Redis를 사용할 수 있도록 확장하였다. 로그인, 회원가입, 비밀번호 재설정 같은 rate limit은 단일 프로세스 메모리에만 저장하면 로드밸런싱 환경에서 인스턴스별로 제한이 분리된다. 개선된 구조에서는 Redis가 설정되어 있을 때 sliding window 형태의 rate limit을 Redis sorted set으로 관리하고, Redis가 없을 때만 기존 메모리 기반 제한으로 되돌아간다. 이로써 백엔드 인스턴스 수가 늘어나도 인증 관련 남용 방지 정책이 전역적으로 적용된다.

### 6.4 결과 비교 및 평가

기존 온라인 컴파일러와 본 작품을 비교하면 가장 큰 차이는 컴파일러 내부 시각화와 문제 풀이 기능이 동시에 제공된다는 점이다. 일반 온라인 컴파일러는 코드 실행을 간편하게 수행하는 데 강점이 있다. 사용자는 여러 언어를 선택하고 코드를 실행하여 stdout을 확인할 수 있다. 그러나 대부분의 서비스는 AST, SSA, IR, ASM과 같은 컴파일러 내부 산출물을 보여주지 않는다. 반대로 온라인 저지는 문제와 채점에 특화되어 있어 정답 여부와 제출 이력을 제공하지만, 사용자가 작성한 코드가 내부적으로 어떻게 변환되는지는 설명하지 않는다.

본 작품은 이 두 영역을 연결한다. 사용자는 B++ 코드를 작성하고 실행 결과를 확인할 뿐 아니라, 같은 코드가 AST, SSA, IR, ASM으로 어떻게 표현되는지 확인할 수 있다. 또한 문제 풀이 화면에서 코드를 저장하고 채점받을 수 있으며, 제출 이력과 컴파일 큐를 통해 결과를 다시 추적할 수 있다. 커뮤니티는 문제별 질의응답을 지원하여 사용자가 단순히 결과를 받는 데 그치지 않고, 학습 과정에서 생기는 질문을 기록하고 공유할 수 있게 한다.

| 비교 항목 | 일반 온라인 컴파일러 | 본 작품 |
|---|---|---|
| 코드 실행 | 지원 | 지원 |
| 다중 언어 | 지원하는 경우 많음 | B++, C, C++, Python, Java, JavaScript 지원 |
| 컴파일러 내부 시각화 | 대부분 미지원 | AST, SSA, IR, ASM 제공 |
| 소스맵 기반 연결 | 미지원 | ASM 등 산출물과 소스 범위 매핑 |
| 온라인 저지 | 별도 서비스인 경우 많음 | 문제 풀이와 채점 통합 |
| 큐/제출 이력 | 제한적 | 사용자·문제·판정 기준 조회 |

언어 관점에서도 B++는 기존 범용 언어와 다른 목표를 가진다. 본 프로젝트가 C++, Python, JavaScript 같은 기존 언어 실행을 함께 지원하는 이유는 사용자가 익숙한 언어로도 문제를 풀 수 있게 하기 위해서이다. 그러나 컴파일러 내부 산출물, tagged metadata, complexity contract, source-aware JSON은 B++에 특화된 연구 축이다. 따라서 B++의 평가는 단순히 실행 가능한 언어 수가 아니라, 알고리즘 코드의 비용 구조를 얼마나 설명 가능한 형태로 만들었는지를 기준으로 보아야 한다.

평가 관점에서 보면 본 작품은 교육용 컴파일러 플랫폼으로서 충분한 차별성을 가진다. 단순히 여러 언어를 실행하는 기능은 이미 많은 서비스가 제공하지만, B++ 컴파일러의 내부 표현을 웹에서 보여주고, 이를 문제 풀이 및 제출 흐름과 결합한 점은 본 작품의 고유한 가치이다. 특히 source map 기반 ASM 하이라이트는 컴파일러와 프론트엔드가 함께 개선되어야 가능한 기능으로, 웹 서비스와 컴파일러 구현이 서로 연결된 캡스톤 프로젝트의 성격을 잘 보여준다.

## 7. 문제점 및 해결 방안

### 7.1 문제점 분석

현재 작품은 제품 수준에 가까운 주요 기능을 제공하지만, 완성된 상용 서비스나 완성된 계약형 언어라고 보기에는 여전히 보완해야 할 한계가 있다. 첫째, B++ 컴파일러의 source map 품질은 컴파일러가 제공하는 span 정보의 정확도에 의존한다. 프론트엔드는 사용자가 선택한 범위와 source range가 겹치는지를 판정할 수 있지만, source range 자체가 statement 단위로 너무 넓거나 expression 단위로 충분히 세밀하지 않다면 하이라이트 역시 넓게 표시될 수밖에 없다. 따라서 소스맵 기능은 프론트엔드만의 문제가 아니라 컴파일러의 AST span, SSA instruction, IR, ASM emission 단계가 함께 정밀해져야 하는 문제이다.

둘째, complexity contract는 아직 보수적 분석 기반이라는 한계가 있다. 일반 프로그램의 시간복잡도와 공간복잡도를 모든 입력과 모든 제어 흐름에 대해 자동 증명하는 것은 매우 어렵다. 특히 포인터 alias, 동적 dispatch, 재귀 종료 조건, 사용자 정의 컨테이너, 외부 함수 호출, 데이터 의존 loop bound가 섞이면 컴파일러가 안전하게 결론을 내리기 어렵다. 따라서 현재 B++의 계약형 분석은 "증명 가능한 경우에는 설명하고, 증명하지 못한 경우에는 실패 이유를 source range와 함께 제공한다"는 방향으로 보아야 한다. 이는 기능의 약점이기도 하지만, 잘못된 확신을 주지 않기 위한 필요한 제약이기도 하다.

셋째, 최적화 metadata와 실제 성능 사이에는 검증 간극이 남아 있다. loop optimizer가 `O(n)` 후보를 만들거나 escape analysis가 stack lowering을 적용하더라도, 실제 실행 시간은 캐시, branch prediction, allocator 상태, 입력 분포, backend codegen 품질에 영향을 받는다. 따라서 complexity report는 실제 벤치마크와 함께 해석되어야 하며, 향후에는 golden source map test뿐 아니라 microbenchmark와 fragmentation benchmark, compile-time budget 측정도 함께 관리해야 한다.

넷째, Docker 샌드박스는 기본적인 격리를 제공하지만 운영 환경에서는 추가 보안 정책이 필요하다. 현재 구조는 네트워크 비활성화, read-only 파일 시스템, 자원 제한, capability 제거 같은 기본 제한을 적용하지만, 공개 서비스로 장기간 운영하려면 seccomp, AppArmor, 컨테이너 이미지 취약점 스캔, 실행별 로그 감사, 실행 결과 보존 정책이 더해져야 한다. 특히 사용자 코드 실행 서비스는 보안 관점에서 공격 표면이 넓기 때문에, "컨테이너에서 실행한다"는 사실만으로 충분하다고 볼 수 없다.

다섯째, 문제 데이터는 20개로 기본 학습 흐름을 보여주기에 충분하지만, 실제 교육 운영을 위해서는 난이도별 문제 수와 hidden case 품질을 더 확장해야 한다. 문제 수가 적으면 사용자는 서비스의 기능을 확인할 수는 있지만, 장기 학습 플랫폼으로 사용하기에는 콘텐츠가 부족하다. 또한 테스트 케이스 품질이 낮으면 정답이 아닌 코드가 통과하거나, 반대로 올바른 코드가 실패할 수 있다. 따라서 문제 데이터는 단순히 개수를 늘리는 것뿐 아니라 난이도, 태그, 설명 품질, 예제, 채점 케이스가 함께 관리되어야 한다.

여섯째, 모바일 화면은 접근 가능하지만 IDE처럼 정보량이 많은 화면에서는 작은 화면 사용성이 제한된다. 그림 13과 그림 14에서 확인할 수 있듯이 문제 목록은 모바일에서도 비교적 자연스럽게 표시되지만, 코드 편집기, AST/SSA/IR/ASM 패널, 출력 콘솔을 동시에 사용하는 IDE 경험은 작은 화면에 그대로 담기 어렵다. 따라서 모바일은 문제 확인, 제출 이력 조회, 커뮤니티 확인 같은 흐름에 적합하고, 복잡한 컴파일러 분석은 데스크톱 환경이 더 적합하다.

일곱째, 운영 관측성은 더 고도화할 필요가 있다. 컴파일 큐 화면을 통해 작업과 판정을 볼 수 있지만, 평균 실행 시간, 실패율 변화, 시간대별 요청량, 문제별 시간 초과 비율, 사용자별 요청 집중도 같은 운영 지표는 아직 충분히 시각화되어 있지 않다. 서비스 사용자가 늘어날수록 단순 목록 조회만으로는 병목을 찾기 어려우므로, 운영 대시보드와 지표 수집 체계를 보완해야 한다.

### 7.2 해결 방안 및 개선 방향

가장 먼저 개선해야 할 부분은 소스맵 고도화이다. 컴파일러는 AST node id, origin node id, SSA instruction id, IR instruction id, ASM segment, byte offset, generated 여부를 안정적으로 제공해야 한다. 프론트엔드는 이 정보를 받아 Monaco Editor의 UTF-16 column 체계와 컴파일러의 byte column 체계 사이를 정확하게 변환해야 한다. 또한 하나의 소스 범위가 여러 ASM 라인으로 내려가는 경우와, 하나의 ASM 라인이 여러 소스 범위에 걸쳐 생성되는 경우를 UI에서 구분하여 표시할 필요가 있다. 이렇게 해야 사용자가 특정 식이나 문장을 선택했을 때 과도하게 넓은 영역이 칠해지는 문제를 줄일 수 있다.

계약형 분석은 표준 라이브러리 summary와 사용자 코드 분석을 함께 고도화해야 한다. `sort`, `binary_search`, `push`, `reserve`, `slice`, `map`, `reduce` 같은 표준 함수와 컨테이너 연산은 시간·공간 비용 요약을 가져야 하며, 컴파일러는 call graph를 따라 이 요약을 합성해야 한다. 사용자 정의 함수에 대해서는 loop trip count, recursion depth, allocation site, alias proof, escape result를 source range와 함께 수집해야 한다. 증명하지 못한 경우에는 단순히 실패로 끝내지 않고, "재귀 종료 조건을 추론하지 못함", "loop bound가 입력 값에 의존하지만 상한을 찾지 못함", "외부 호출의 비용 summary가 없음"처럼 사용자가 고칠 수 있는 이유를 report해야 한다.

최적화 신뢰성을 높이기 위해서는 source map golden test와 성능 benchmark를 함께 운영해야 한다. source map test는 "이 소스 범위가 정확히 어떤 AST/SSA/ASM에 연결되는가"를 검증하고, benchmark는 실제 최적화가 컴파일 시간과 실행 시간, 메모리 사용량에 어떤 영향을 주는지 측정한다. 특히 compiler optimization은 pass를 많이 추가한다고 항상 좋아지는 것이 아니므로, pass별 반복 횟수와 code size growth, specialization threshold, compile-time budget을 문서화하고 측정 결과에 따라 조정하는 체계가 필요하다.

샌드박스 보안은 현재의 Docker 제한 위에 한 단계 더 강화되어야 한다. seccomp와 AppArmor profile을 적용하면 시스템 호출과 파일 접근 범위를 더 세밀하게 제한할 수 있다. 컨테이너 이미지는 주기적으로 취약점 스캔을 수행하고, 실행에 필요한 최소 패키지만 포함하도록 경량화해야 한다. 또한 실행별 로그 감사와 실패 원인 기록을 남기면, 비정상적인 실행 패턴을 추적하고 서비스 장애를 분석하는 데 도움이 된다. 공개 운영 환경에서는 보안 정책이 기능 구현만큼 중요하므로, 샌드박스는 지속적으로 검증되어야 한다.

문제 데이터는 난이도별로 확장해야 한다. 현재 20개 문제는 기본 흐름을 보여주기에 적합하지만, 학습 플랫폼으로 발전하려면 입문, 기초 문법, 배열과 문자열, 함수, 자료구조, 알고리즘, 컴파일러 개념 실습처럼 단계별 문제 구성이 필요하다. 또한 각 문제는 명확한 설명, 충분한 예제, 품질 높은 채점 케이스를 갖추어야 한다. 문제 생성과 수정 UI에서도 입력 형식, 출력 형식, 제한 시간, 메모리 제한, 테스트 케이스 유효성 검사를 강화하면 운영자가 문제를 추가할 때 오류를 줄일 수 있다.

모바일 UX는 데스크톱 IDE를 단순히 반응형으로 줄이는 방식에서 벗어나야 한다. 문제 확인, 제출 이력, 커뮤니티, 리더보드 같은 화면은 모바일에 비교적 잘 맞지만, AST/SSA/IR/ASM 분석을 포함한 IDE는 작은 화면에서 복잡하다. 따라서 모바일에서는 문제 읽기와 간단한 코드 수정, 제출 결과 확인을 중심으로 하고, 깊은 컴파일러 분석은 데스크톱 화면에서 수행하도록 흐름을 분리하는 것이 현실적이다. 예를 들어 모바일 IDE에서는 분석 패널을 기본으로 접어두고, 필요할 때 전체화면 모달로 열 수 있게 하는 방식이 적합하다.

운영 관측성도 중요한 개선 방향이다. 현재 큐 화면은 작업 목록과 문제별/사용자별 집계를 제공하지만, 장기 운영에서는 더 많은 지표가 필요하다. 평균 컴파일 시간, 평균 실행 시간, 메모리 초과 비율, 시간 초과 비율, 문제별 실패율, 사용자별 요청량, 시간대별 트래픽을 수집하고 대시보드에서 시각화하면 운영자는 장애를 더 이른 시점에 파악할 수 있다. 또한 WebSocket 기반 실시간 업데이트를 적용하면 사용자는 새로고침 없이도 자신의 작업 상태 변화를 확인할 수 있다.

마지막으로 라이선스와 재현성을 보완해야 한다. Python 의존성 버전 고정, Node 패키지 잠금 파일 검증, Docker 이미지 식별값 고정, 소프트웨어 구성 목록 생성, B++ 컴파일러 라이선스 확인은 공개 배포 서비스의 신뢰성을 높인다. 특히 컴파일러 바이너리, 표준 라이브러리, 실행 wrapper, 컨테이너 이미지는 같은 버전 단위로 추적되어야 한다. 배포 시점의 commit hash, 패키지 checksum, 이미지 digest를 기록하면 서버에서 발생한 컴파일 오류를 나중에 같은 환경으로 재현할 수 있다. 이러한 보완은 캡스톤 이후 서비스를 장기간 유지할 때 중요하다.

## 8. 결론

### 8.1 연구 결과 요약

본 프로젝트는 웹 기반 B++ 온라인 컴파일러와 학습 플랫폼을 구현하였다. 사용자는 브라우저에서 코드를 작성하고, 컴파일하고, 실행하고, 문제를 제출할 수 있다. 또한 AST, SSA, IR, ASM 시각화를 통해 컴파일러 내부 구조를 관찰할 수 있다. 이 과정에서 프론트엔드, 백엔드, 샌드박스, 데이터베이스, 배포 자동화가 하나의 서비스로 통합되었다. 사용자는 메인 IDE에서 언어 기능을 자유롭게 실험할 수 있고, 문제 화면에서는 문제별 코드 저장과 채점을 수행할 수 있으며, 제출 이력과 큐를 통해 결과를 추적할 수 있다.

구현 결과, IDE, 컴파일러 시각화, 터미널, 문제 풀이, 채점, 제출 이력, 컴파일 큐, 리더보드, 커뮤니티, 인증, 비밀번호 재설정, 서버 배포까지 하나의 서비스로 통합하였다. 특히 Docker 샌드박스와 PostgreSQL 기반 데이터 보존 구조를 적용하여 단순 데모를 넘어 실제 운영 가능한 구조를 갖추었다. B++ 컴파일러는 표준 라이브러리와 함께 배포 단위로 정리되며, source map JSON을 통해 ASM 등 컴파일 산출물과 원본 소스 범위를 연결할 수 있도록 하였다. 이는 웹 서비스 구현과 컴파일러 구현이 서로 맞물린 결과이다.

또한 본 프로젝트는 B++를 알고리즘에 최적화된 언어로 발전시키기 위한 컴파일러 기반을 정리하였다. B++ 컴파일러는 AST, SSA, IR, ASM을 단순 문자열로 출력하는 수준을 넘어 source range, stable id, generated metadata를 포함한 JSON 산출물을 제공하도록 확장되었다. 이를 통해 웹 IDE는 컴파일러 내부 표현을 정확히 시각화할 수 있고, 향후 시간복잡도와 공간복잡도 예산을 source range와 연결하여 사용자에게 설명하는 계약형 컴파일러 기능으로 확장할 수 있다. 즉 본 작품의 결과는 온라인 실행 플랫폼과 알고리즘 최적화 언어 연구의 기반을 동시에 포함한다.

### 8.2 연구의 의의 및 한계점

본 연구의 의의는 컴파일러 학습과 온라인 저지 기능을 결합했다는 점이다. 사용자는 정답 여부뿐 아니라 코드가 컴파일러 내부에서 어떻게 변환되는지 함께 확인할 수 있다. 이는 컴파일러 교육, 프로그래밍 언어 실험, 알고리즘 문제 풀이를 하나의 흐름으로 연결한다. 특히 AST, SSA, IR, ASM을 한 화면에서 제공하는 구조는 학습자가 추상적인 컴파일러 개념을 실제 코드와 연결하도록 돕는다. 또한 문제 풀이와 커뮤니티를 결합하여 단순 실행 실험을 넘어 지속적인 학습 플랫폼으로 확장할 수 있는 기반을 마련하였다.

언어 설계 측면에서의 의의는 B++가 단순 문법 실험이 아니라 알고리즘 코드의 비용 구조를 컴파일러가 이해하는 방향을 지향한다는 점이다. 시간복잡도와 공간복잡도 예산, loop trip count, allocation, alias, escape, number storage, container growth 같은 요소를 컴파일러가 분석하고 report할 수 있다면, 학습자는 왜 어떤 풀이가 시간 초과나 메모리 초과에 가까운지 더 일찍 이해할 수 있다. 이는 온라인 저지의 최종 판정 중심 피드백을 컴파일 단계의 구조적 피드백으로 확장하는 시도이다.

한계도 존재한다. 현재 문제 데이터와 채점 정책은 교육용 기본 수준이며, 대규모 운영을 위해서는 더 많은 문제, 더 정교한 테스트 케이스, 부정 행위 방지, 실행 자원 관측, 보안 정책 강화가 필요하다. source map 기반 하이라이트는 컴파일러가 제공하는 span 정보의 품질에 의존하므로, 컴파일러 쪽의 지속적인 개선이 필요하다. 또한 모바일 환경에서는 복잡한 그래프 분석 경험이 제한적이므로, 데스크톱과 모바일의 사용 흐름을 분리하는 UX 개선이 요구된다.

계약형 최적화 역시 아직 완전 자동 증명 단계라고 보기는 어렵다. 일반 프로그램의 시간복잡도와 공간복잡도를 모든 경우에 정확히 증명하는 것은 매우 어려운 문제이므로, B++는 우선 알고리즘 풀이에서 자주 나타나는 반복문, slice/Vec 접근, 표준 라이브러리 호출, 명확한 재귀 구조, 명확한 allocation 패턴을 중심으로 보수적인 분석을 제공해야 한다. 따라서 향후 과제는 더 많은 패턴을 안전하게 증명하고, 증명하지 못한 경우에는 그 이유를 사용자에게 이해 가능한 방식으로 설명하는 것이다.

### 8.3 향후 연구 방향

향후 연구는 B++ 컴파일러 source map을 더 정밀하게 활용하는 방향으로 진행할 수 있다. 현재도 source range와 offset 기반 매핑을 제공하지만, expression 단위 하이라이트와 AST, SSA, IR, ASM 간 cross-navigation을 강화하면 교육적 가치가 더 커진다. 사용자가 AST 노드를 선택하면 관련 SSA instruction과 ASM line이 함께 표시되고, ASM line을 선택하면 원본 소스와 IR 단계까지 거슬러 올라갈 수 있는 구조가 가능하다. 이는 컴파일러 내부 단계를 개별 탭으로 보는 수준을 넘어, 변환 과정 전체를 탐색하는 도구로 발전시키는 방향이다.

컴파일러 연구 측면에서는 시간복잡도와 공간복잡도 budget을 실제 언어 기능으로 끌어올리는 작업이 중요하다. 함수나 블록에 `time <= O(n log n)`, `space <= O(n)`과 같은 계약을 부여하고, 컴파일러가 이를 SSA와 optimization metadata를 통해 추적하는 구조를 발전시킬 수 있다. 이때 완전 증명을 목표로 하기보다, 증명 가능한 경우에는 통과시키고 증명하지 못한 경우에는 경고와 source range를 제공하는 보수적 접근이 현실적이다. 이러한 기능이 구현되면 B++는 단순히 문제를 풀 수 있는 언어가 아니라, 풀이의 비용 구조를 설명하고 개선 방향을 제안하는 알고리즘 학습 언어가 된다.

문제 추천과 학습 경로도 향후 중요한 확장 방향이다. 현재는 사용자가 직접 문제를 검색하고 선택하지만, 난이도, 태그, 이전 제출 결과를 기반으로 다음 문제를 추천할 수 있다면 학습 흐름이 더 자연스러워진다. 예를 들어 반복문 문제에서 자주 오답을 낸 사용자는 배열 문제로 바로 넘어가기보다 반복문 기초 문제를 더 풀도록 안내받을 수 있다. 태그 기반 커리큘럼을 구성하면 B++ 문법 학습과 알고리즘 학습을 단계적으로 연결할 수 있다.

운영 측면에서는 WebSocket 기반 실시간 큐 업데이트와 관측 대시보드 고도화가 필요하다. 사용자는 자신의 제출이 대기 중인지, 실행 중인지, 완료되었는지를 새로고침 없이 확인할 수 있어야 한다. 운영자는 시간대별 요청량, 실패율, 평균 실행 시간, 메모리 사용량, 문제별 오류 분포를 확인할 수 있어야 한다. 이러한 지표는 서비스가 커질수록 장애 대응과 품질 개선의 근거가 된다.

보안과 재현성 역시 향후 연구의 중요한 축이다. 샌드박스 보안 정책을 강화하고, 빌드 재현성을 높이며, 의존성 버전을 명확히 고정하면 공개 운영 환경에 더 적합한 서비스가 된다. 특히 컴파일러와 표준 라이브러리, 런타임 wrapper, 컨테이너 이미지를 같은 버전 단위로 묶고, 배포 시점의 정확한 commit과 checksum을 기록하는 체계가 필요하다.

결론적으로 B++는 단순한 코드 실행 환경이 아니라, 알고리즘 풀이의 비용 구조를 언어와 컴파일러가 함께 설명하려는 시도이다. 본 작품은 그 기반으로 온라인 IDE, 온라인 저지, 컴파일러 시각화, source-aware JSON, complexity budget 모델을 하나의 흐름으로 통합하였다. 향후에는 source map 정밀도, 표준 라이브러리 비용 summary, loop/alias/escape 분석, 문제 데이터 품질, 운영 관측성, 보안 정책을 지속적으로 개선함으로써 장기 운영에 적합한 학습 플랫폼이자 계약형 알고리즘 언어로 발전할 수 있다.

```bpp
func main_parse_cli(argc: u64, argv_ptr: *u64) -> MainCliParseResult {
    var result: MainCliParseResult;
    result.ok = 0;
    result.filename = 0;
    result.target_override = 0;
    result.ast_filter_func_name = slice(0, 0);
    result.ast_filter_module_name = slice(0, 0);
    result.ast_filter_no_std = 0;

    opt_init_defaults();
    annotation_set_symbolic_report_enabled(0);
    annotation_set_complexity_require_std_summaries(0);

    if (argc < 2) { return result; }

    var filename: u64 = 0;
    for (var i: u64 = 1; i < argc; i++) {
        var arg: u64 = argv_ptr[i];
        var arg_len: u64 = str_len(arg);

        if (str_eq(slice(arg, arg_len), slice("-O1", str_len("-O1")))) {
            opt_set_level(1);
            continue;
        }
        if (str_eq(slice(arg, arg_len), slice("-O2", str_len("-O2")))) {
            opt_set_level(2);
            continue;
        }
        if (str_eq(slice(arg, arg_len), slice("-dump-ast-json", str_len("-dump-ast-json")))) {
            opt_set_output_mode(OUT_AST_JSON);
            continue;
        }
        if (str_eq(slice(arg, arg_len), slice("-dump-ssa-json", str_len("-dump-ssa-json")))) {
            opt_set_ir_mode(IR_SSA);
            opt_set_output_mode(OUT_IR_JSON);
            continue;
        }
        if (str_eq(slice(arg, arg_len), slice("--emit-source-map", str_len("--emit-source-map")))) {
            opt_set_output_mode(OUT_SOURCE_MAP);
            continue;
        }
        if (str_eq(slice(arg, arg_len), slice("--emit-json", str_len("--emit-json")))) {
            opt_set_output_mode(OUT_UNIFIED_JSON);
            continue;
        }
        if (str_eq(slice(arg, arg_len), slice("--source-map-user-only", str_len("--source-map-user-only")))) {
            opt_source_map_set_user_only(1);
            continue;
        }
        if (str_eq(slice(arg, arg_len), slice("--source-map-file", str_len("--source-map-file")))) {
            if (i + 1 >= argc) {
                emit_stderr("[ERROR] missing value for --source-map-file\n");
                return result;
            }
            i = i + 1;
            opt_source_map_set_file(argv_ptr[i], str_len(argv_ptr[i]));
            continue;
        }
    }
    result.filename = filename;
    result.ok = filename != 0;
    return result;
}

func main_emit_source_map_stdout(merged_prog: *AstProgram) -> u64 {
    diag_reset();
    if (opt_source_map_user_only() != 0 && opt_source_map_file_ptr() != 0) {
        asm_source_capture_set_filter_file(opt_source_map_file_ptr(), opt_source_map_file_len());
    }
    asm_source_capture_start(1);
    program_with_sigs(merged_prog, get_func_sigs());
    asm_source_capture_stop();
    asm_source_capture_clear_filter();
    if (diag_has_errors() != 0) {
        emit_stderr("[ERROR] ASM source map generation failed\n");
        return 1;
    }
    asm_source_capture_dump_json();
    return 0;
}

func main_emit_unified_json_stdout(
    merged_prog: *AstProgram,
    ast_filter: *AstDumpFilter,
    source_file: u64,
    source_file_len: u64
) -> u64 {
    emit("{\"schemaVersion\":1,\"sourceRangeSemantics\":{\"endColumn\":\"exclusive\",\"columnEncoding\":\"byte\",\"offsetEncoding\":\"byte\"},\"views\":{\"ast\":");
    ast_dump_program_json_filtered(merged_prog, ast_filter);

    emit(",\"ssa\":");
    var old_ir_mode: u64 = opt_get_ir_mode();
    opt_set_ir_mode(IR_SSA);
    diag_reset();
    program_with_sigs_ir_json(merged_prog, get_func_sigs());
    opt_set_ir_mode(old_ir_mode);
    if (diag_has_errors() != 0) { return 1; }

    emit(",\"asm\":");
    diag_reset();
    if (opt_source_map_user_only() != 0) {
        if (opt_source_map_file_ptr() != 0) {
            asm_source_capture_set_filter_file(opt_source_map_file_ptr(), opt_source_map_file_len());
        } else {
            asm_source_capture_set_filter_file(source_file, source_file_len);
        }
    }
    asm_source_capture_start(1);
    program_with_sigs(merged_prog, get_func_sigs());
    asm_source_capture_stop();
    asm_source_capture_clear_filter();
    if (diag_has_errors() != 0) { return 1; }
    asm_source_capture_dump_json();
    emit("}}\n");
    return 0;
}
```

```bpp
func ssa_loop3_trip_no_wrap_u64(init: u64, bound: u64, step: u64, inclusive: u64, trip_out: *u64) -> u64 {
    if (step == 0 || trip_out == 0) { return 0; }
    var max: u64 = 0 - 1;
    *trip_out = 0;
    if (inclusive != 0) {
        if (init > bound) { return 1; }
        if (bound > max - step) { return 0; }
        *trip_out = ((bound - init) / step) + 1;
        return 1;
    }
    if (init >= bound) { return 1; }
    if (bound > (max - step) + 1) { return 0; }
    *trip_out = ((bound - 1 - init) / step) + 1;
    return 1;
}

func ssa_loop3_inst_hoistable(fn: *SSAFunction, info: *SSALoop3Info, inst: *SSAInstruction) -> u64 {

    if (ssa_loop3_operand_defined_in_loop(fn, info, inst.src1) != 0) { return 0; }

func ssa_loop3_licm(fn: *SSAFunction, info: *SSALoop3Info, summary: *SSALoop3Summary) -> u64 {
    if (fn == 0 || info == 0 || info.preheader == 0 || info.body_blocks == 0) { return 0; }
    if (info.side_effect_count != 0 || info.nested_count != 0 || info.latch_count != 1) { return 0; }
    var changed: u64 = 0;
    var moved: u64 = 0;
    var n: u64 = info.body_blocks.len();
    for (var i: u64 = 0; i < n; i = i + 1) {
        var b: *SSABlock = info.body_blocks.get(i);
        if (b == 0 || b == info.preheader) { continue; }
        var cur: *SSAInstruction = b.inst_head;
        while (cur != 0 && moved < 4) {
            var next: *SSAInstruction = cur.next;
            var op: u64 = op_of(cur);
            if (op != SSA_OP_JMP && op != SSA_OP_BR && op != SSA_OP_RET &&
                ssa_loop3_inst_hoistable(fn, info, cur) != 0 &&
                ssa_loop3_unlink_inst(b, cur) != 0) {
                insert_before_terminator(info.preheader, cur);
                changed = changed + 1;
                moved = moved + 1;
            }
            cur = next;
        }
    }
    return changed;
}

func ssa_loop3_strength_reduce_inst(fn: *SSAFunction, cur: *SSAInstruction) -> u64 {
    if (cur == 0) { return 0; }
    var op: u64 = op_of(cur);
    var lhs: u64 = 0;
    var rhs: u64 = 0;
    var lhs_const: u64 = ssa_loop3_operand_const_value(fn, cur.src1, &lhs);
    var rhs_const: u64 = ssa_loop3_operand_const_value(fn, cur.src2, &rhs);
    if (op == SSA_OP_MUL) {
        if (lhs_const != 0 && lhs == 1) { set_op(cur, SSA_OP_COPY); cur.src1 = cur.src2; cur.src2 = 0; return 1; }
        if (rhs_const != 0 && rhs == 1) { set_op(cur, SSA_OP_COPY); cur.src2 = 0; return 1; }
        if (lhs_const != 0 && ssa_loop3_is_pow2(lhs) != 0) {
            set_op(cur, SSA_OP_SHL);
            cur.src1 = cur.src2;
            cur.src2 = operand_const(ssa_loop3_log2_pow2(lhs));
            return 1;
        }
        if (rhs_const != 0 && ssa_loop3_is_pow2(rhs) != 0) {
            set_op(cur, SSA_OP_SHL);
            cur.src2 = operand_const(ssa_loop3_log2_pow2(rhs));
            return 1;
        }
    }
    if (op == SSA_OP_UDIV && rhs_const != 0 && ssa_loop3_is_pow2(rhs) != 0) {
        set_op(cur, SSA_OP_SHR);
        cur.src2 = operand_const(ssa_loop3_log2_pow2(rhs));
        return 1;
    }
    if (op == SSA_OP_UMOD && rhs_const != 0 && ssa_loop3_is_pow2(rhs) != 0) {
        set_op(cur, SSA_OP_AND);
        cur.src2 = operand_const(rhs - 1);
        return 1;
    }
    return 0;
}
```

```bpp
func bpp_heap_policy_uses_gc(lifecycle: u64, ownership: u64, barrier: u64) -> u64 {
    if (ownership == BPP_TAG_OWN_SHARED || ownership == BPP_TAG_OWN_ESCAPED) { return 1; }
    if (lifecycle == BPP_TAG_LIFE_PINNED || lifecycle == BPP_TAG_LIFE_OLD) { return 1; }
    if (barrier == BPP_TAG_BARRIER_DIRTY) { return 1; }
    return 0;
}

func bpp_heap_alloc_tagged(size: u64, lifecycle: u64, ownership: u64, storage: u64, barrier: u64, shape: u64, profiled: u64) -> u64 {
    if (storage != BPP_TAG_STORAGE_HEAP) {
        bpp_tag_allocator_record_denied_alloc(lifecycle, ownership, storage);
        return 0;
    }
    if (bpp_heap_policy_uses_gc(lifecycle, ownership, barrier) != 0) {
        var gc_ptr: u64 = bpp_gc_alloc_tagged_policy(size, lifecycle, ownership, barrier, shape);
        if (gc_ptr == 0 || profiled == 0) { return gc_ptr; }
        return bpp_tag_repack_shape_profiled(gc_ptr, shape, profiled);
    }
    var ptr: u64 = heap_alloc(size);
    if (ptr == 0) { return 0; }
    bpp_tag_allocator_record_alloc(lifecycle, ownership, storage);
    return bpp_tag_pack(ptr, lifecycle, ownership, storage, barrier, shape, profiled);
}

func bpp_stack_alloc_auto_tagged_from_raw(
    ptr: u64,
    size: u64,
    escapes: u64,
    address_taken: u64,
    shared: u64,
    pinned: u64,
    immortal: u64,
    arena_hint: u64,
    shape: u64
) -> u64 {
    var policy: BppEscapePolicy = bpp_escape_policy_for(size, escapes, address_taken, shared, pinned, immortal, arena_hint);
    if (policy.storage == BPP_TAG_STORAGE_STACK) {
        return bpp_stack_materialize_tagged_raw(ptr, policy.lifecycle, policy.ownership, policy.barrier, shape, 0);
    }
    return bpp_heap_alloc_with_policy(size, &policy, shape);
}

func bpp_gc_generation_for_lifecycle(lifecycle: u64) -> u64 {
    if (lifecycle == BPP_TAG_LIFE_OLD || lifecycle == BPP_TAG_LIFE_PINNED || lifecycle == BPP_TAG_LIFE_IMMORTAL) { return 2; }
    return 1;
}

func bpp_gc_alloc_tagged_policy(size: u64, lifecycle: u64, ownership: u64, barrier: u64, shape: u64) -> u64 {
    if (size == 0) { return 0; }
    bpp_gc_auto_collect_before_alloc(size);
    var raw: u64 = heap_alloc(size);
    if (raw == 0) { return 0; }
    var tagged_ptr: u64 = bpp_tag_pack(raw, lifecycle, ownership, BPP_TAG_STORAGE_HEAP, barrier, shape, 0);
    if (bpp_gc_register_block_policy(tagged_ptr, size, shape, lifecycle) == 0) {
        heap_free(raw);
        return 0;
    }
    return tagged_ptr;
}
```
