# v15 컴파일러 회귀 수정과 일반 컴파일 성능

## 범위와 비교 기준

아래 20개 프로파일은 2026-09-28 Windows x86-64에서 측정한 Candidate 31 기준이다. 이후 Linux 검증에서 발견한 문제와 Candidate 35 결과는 마지막 절에 별도로 기록한다. 모든 Bpp 컴파일러와 생성된 실행 파일에는 프로세스당 4GiB 제한을 적용했다.

Candidate 20은 962개 중 127개가 실패하므로 성능 비교 기준으로 사용하지 않았다. GC·Number 회귀를 수정하고 Windows 전체 테스트를 통과한 `corrected-baseline.exe`와 당시 완료본 Candidate 31을 비교한다. 기존 미커밋 변경은 보존했다.

## 실제 구현 변경

- GC 런타임 포함 여부를 결정하기 전에 타입 기반 GC 프레임 필요성을 확인한다. 뒤늦게 생성되는 Number/사용자 연산자 호출도 정확한 호출 대상에 연결한다.
- 중첩 단항 연산의 임시 수신자를 일반 메서드 호출 경로에서 처리한다. 전체 프로그램을 분석하는 IR·계약 출력에는 미사용 표준 라이브러리 본문도 정상적으로 lowering한다.
- 구조체·배열 포인터의 원소 크기를 전체 타입 정보로 계산한다. 양쪽 백엔드의 인덱싱·포인터 산술을 같은 규칙으로 통합하고 `Vec<T>.get`은 직접 타입 기반 읽기를 사용한다.
- GC 객체 인덱스를 객체 수에 따라 두 배씩 확장한다. 고정 8192개 버킷에서 길어진 연결 목록을 계속 탐색하던 비용을 제거한다. 확장 실패 시 기존 인덱스와 안전한 대체 탐색 경로를 보존한다.
- 전역·구조체·메서드 조회에 이름 인덱스를 사용하고, 메서드 후보마다 같은 수신자 타입을 다시 찾지 않는다. 추가 등록, 모호성, 이름 변경, 컴파일 컨텍스트 분리를 검사한다.
- 일반 legacy 함수의 최소 2KiB 스택 예약을 없애고 실제 지역 변수·인자·임시 값에 맞춘다. 명시적 스택 설정, 인라인 어셈블리의 기존 예약 공간, 큰 지역 변수와 Windows 스택 프로브는 유지한다.
- SSA 명령 출력 중 지역 객체 크기·임시 슬롯·보존 레지스터 분석을 함수당 한 번 수행한다. 출력 구간 밖에는 결과를 재사용하지 않아 같은 함수 객체가 수정되어도 이전 크기가 남지 않는다.

## 성능 측정

최종 20개 프로파일 모두 측정 중앙값이 감소했다. 일반 소형·중형 입력은 약 10~24%, 무거운 모듈 입력은 39~51%, 컴파일러 전체 소스는 63~68% 감소했다. strict SSA 제네릭 입력은 52% 감소했다. **모든 프로그램이 같은 비율로 빨라진다는 뜻은 아니다.** 이 PC의 대표 입력을 반복 측정한 결과이며 다른 하드웨어·프로젝트의 동일한 개선 폭을 보장하지 않는다.

측정 조건:

- 매번 새 프로세스, `--no-cache`, 컴파일러별·입력별 예열 1회, 이후 순서를 번갈아 3~7회 실행하고 중앙값 비교.
- 예열은 운영체제·실행 환경 예열이다. 디스크 캐시까지 비운 측정은 아니며 컴파일 산출물 캐시 적중으로 얻은 수치도 아니다.
- NASM·링커·생성 프로그램 실행 시간은 컴파일 시간에서 제외하고, 별도 정확성 검증에 사용한다.
- 두 컴파일러가 같은 고정 입력과 표준 라이브러리를 사용한다. 이전 비교용 컴파일러의 구조체 포인터 버그 때문에 측정 전용 라이브러리는 기존 `Vec.get` 구현을 유지한다. 실제 소스와 전체 회귀 테스트에는 새 구현과 추가 검사를 그대로 적용한다.
- 측정 전후 컴파일러·입력·의존 파일의 해시를 확인한다. AST 출력과 실패 진단은 동일성을, 어셈블리는 조립·링크 후 실행 결과의 동일성을 검사한다.
- auto-SSA 프로파일은 기존 CLI의 `-dump-ssa`로 SSA를 활성화한 뒤 최종 출력을 `-asm`으로 지정한다. strict SSA는 `--backend ssa`를 사용한다.
- auto-SSA 출력에 섞인 기존 `[DEBUG]` 행은 조립 검증 때만 제거하며, 제거한 행 수를 `validation.json`에 기록한다. 측정 시간과 원본 출력은 그대로 보존한다.
- AST 출력과 오류 진단 프로파일을 제외한 시간은 소스에서 어셈블리까지의 컴파일 시간이다. 테스트 병렬화·테스트 수 축소·캐시 적중 효과를 성능 개선으로 계산하지 않았다.

## 남은 한계

- 소형 입력은 여전히 기본 라이브러리 로딩·파싱 비용이 크다. 이번 대형 입력의 2.7~3.1배 개선을 모든 작은 프로그램에 적용할 수는 없다.
- auto-SSA는 필요한 함수에 legacy 대체 경로를 허용하는 기존 모드다. 전체 컴파일러 소스를 strict SSA만으로 빌드했다는 주장이 아니다.
- 메모리를 줄이는 작업은 아니다. 컴파일러 전체 소스의 legacy 프로세스 최대 작업 집합 중앙값은 약 536MiB에서 540MiB로 소폭 늘었으며, 모든 실행은 4GiB 제한 안에서 통과했다.
- 위 Candidate 31 성능 측정 당시에는 Windows만 검증했다. 후속 Linux 검증은 아래에 구분한다.

## 후속 Linux 회귀 수정: Candidate 35

기존 SSH 연결의 격리된 작업 디렉터리에서 Ubuntu 24.04.4, NASM 2.16.01, Clang 18.1.3으로 검증했다. 수정 전 전체 실행은 1,052개 중 1,013개 통과, 39개 실패였으며 LLVM 제외 항목은 없었다. 실패는 native 어셈블리 15개와 LLVM 빌드·실행·최적화 검증 24개였다.

수정 내용:

- GC 자동 관리가 비활성화된 내부 함수에 write barrier나 불균형 임시 루트 호출을 넣지 않는다. 함수별 GC 프레임 필요성은 SSA 빌드 구간 안에서 한 번만 계산하고 다음 함수에서 초기화한다.
- LLVM ABI 조회의 빈 결과를 명시적으로 초기화한다. 초기화되지 않은 기록 때문에 간접·가변 인자 호출에 `void` 인자가 생성되던 문제를 고쳤다.
- LLVM 매개변수의 실제 레지스터 표현과 타입 조회를 일치시키고, 함수 포인터 전역 변수·초깃값·매개변수·반환 타입을 지원 경로에 포함한다.
- 이미 종료된 SSA 블록 뒤에 문장과 중복 정리 코드를 만들지 않는다.
- 오래된 32바이트 헤더를 가정한 LLVM 전용 가짜 힙 구현을 없애고, 소유권·해제·통계를 공유 Bpp 런타임으로 처리한다. OS 메모리 호출만 LLVM 경계에서 연결한다.
- 호출을 상수 등으로 바꿀 때 호환되지 않는 보조 메타데이터를 제거한다. 호출 메타데이터 번호가 반환값이나 Number 상수로 출력되던 실제 오컴파일을 고쳤다. 메타데이터 소유권은 기존 컴파일 컨텍스트가 유지한다.

기존 회귀 파일에 ABI 빈 결과, 전역 함수 초기값, 보조 메타데이터 수명, 함수 상태 초기화 검사를 추가했다. 테스트 수나 기대값은 줄이지 않았다. Windows 묶음 빌드가 가리던 GC 실패는 기존 try/catch 테스트를 독립 컴파일하도록 검사 조건을 강화했다.

최종 검증 근거:

- Windows 전체 962/962, 테스트 구간 50.4초. 캐시 검사 42/42와 native Stage1/Stage2 실행 파일 일치 통과.
- Windows Stage1/Stage2 SHA-256: `5E14D65D9E0A682D674F4E96A7944E1875294BB554F2A58B3B4DEE69483F5CBA`.
- Linux 집중 검사 96/96, LLVM 제외 0개. 이 중 native 68개는 각각 스트레스 20회·안정성 5회 추가 반복도 통과했다. 전체 빌드 스크립트의 기존 full 모드는 추가 반복 0회가 기본이며 그 설정은 바꾸지 않았다.
- 새 Linux 작업 사본에서 `build_and_test.sh` 종료 코드 0, 전체 1,052/1,052 통과, LLVM 제외 0개. 수정 전 실패한 39개도 모두 통과했다. 자기 빌드를 포함한 전체 시간은 1,405초였다. 수정 전 실행은 1개 작업, 최종 실행은 2개 작업이므로 이 시간 차이를 컴파일러 자체의 속도 개선으로 계산하지 않는다.
- Linux native Stage1/Stage2 어셈블리가 바이트 단위로 같다. 독립된 임시 경로에서 조립한 원본 ELF에는 NASM의 FILE 심볼 경로 차이가 있었다. 같은 조립 경로로 두 출력을 다시 조립한 별도 검사는 심볼 제거 없이 실행 파일 전체 바이트 일치와 종료 코드 0을 확인했다. 원본 파일과 최초 비교 로그도 보존했다.
