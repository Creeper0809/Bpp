# 알고리즘 성능 비교와 네이티브 코드 생성 최적화

2026-10-25에 같은 알고리즘과 입력으로 C++와 Bpp를 비교했다. 수정 전후 Bpp 컴파일러를 함께 유지하고, GCC, Clang, 수정 전후 Bpp native O1, Bpp SSA O1, Bpp LLVM과 Clang O3를 순서를 바꿔 5회씩 실행했다. 10개 알고리즘, 60개 조합, 실측 300개이며, 모든 조합은 독립적인 Python 기대값으로 작은 입력 두 종류와 실제 측정 입력을 확인했다.

## 측정 결과

시간은 프로세스 CPU 시간 중앙값(ms)이다. 데이터 생성 및 초기화, 실행 시작과 최소 입출력을 포함한 전체 작업이며 내부 연산 구간만의 측정은 아니다. 컴파일, 어셈블, 링크는 제외했다. C++ 열은 각 행에서 GCC O3와 Clang O3 중 빠른 값을 사용한다.

수정 후 네이티브 중앙값은 10개 모두 감소했다. 알고리즘별 개선 배율의 기하평균은 1.4701배다. 이 값은 위 고정 작업을 같은 비중으로 비교한 결과이며 임의의 프로그램 전체에 대한 개선 보장은 아니다. 네이티브 출력은 이번 비교에서 여전히 C++보다 느리다. 특히 배낭 DP와 행렬 곱셈에 큰 차이가 남는다. LLVM 열은 별도 백엔드 비교이고, 네이티브 최적화 결과를 이 열로 대신하지 않았다.

## 확인한 병목과 수정

`src/emitter/gen/expr.bpp`와 `stmt.bpp`의 O1 이상 경로를 수정했다.

1. 64비트 정수의 상수 및 단순 지역 변수 RHS를 읽을 때, 왼쪽 결과를 스택에 넣고 빼던 처리를 제거한다. 왼쪽 표현식은 먼저 실행하고 RHS는 그 뒤에 읽는다.
2. 평범한 64비트 정수 지역 변수 저장은 해당 스택 슬롯에 직접 기록한다. 전역 및 별칭 해석, 포인터와 관리 객체 저장은 기존 경로를 유지한다.
3. 1, 2, 4, 8바이트 원소의 주소 계산에 x86 scaled LEA를 사용한다. 주소가 고정된 식별자 배열은 인덱스 평가 후 주소를 구해 불필요한 base spill을 없앤다. 포인터 및 slice는 기존의 base 먼저 평가 규칙을 유지한다.

실제 생성된 알고리즘 함수의 정적 push 개수는 배열 합산 19→7, 배낭 DP 34→11, 행렬 곱셈 62→17로 줄었다. `main`과 런타임은 이 집계에서 제외한다. 이는 생성 코드의 정적 개수이며 실행 중 명령 횟수나 CPU 사이클 수와 같지 않다. [생성 코드 대조 기록](codegen-evidence.json)에 원본 어셈블리 해시와 일부 출력, 명령별 개수를 보존했다.

남은 행렬 곱셈 차이에는 벡터화 여부도 있다. 측정한 Clang C++ 알고리즘 함수에는 packed 정수 연산 `pmuludq`와 `paddq`가 각각 정적으로 6개 있고, Bpp native 함수에는 없다. [실행 파일 대조 기록](matrix-vectorization-evidence.json)은 측정된 바이너리 해시, 함수 범위, 명령 일부를 보존한다. 이 차이는 추가 최적화 방향의 근거이며, 전체 시간 차이를 해당 명령만으로 설명하는 사이클 분석은 아니다.

배열 합산 함수에는 입력 생성용 `next_random` 호출이 Bpp native에 정적으로 1개 남아 있고, 빠른 C++인 GCC 출력의 같은 함수에는 호출이 없다. [생성 코드 대조 기록](codegen-evidence.json)에 C++ 바이너리 해시와 함수 디스어셈블 명령도 포함했다. 작은 함수의 인라인은 후속 최적화 후보이며, 초기화까지 포함한 이번 측정에서 관찰한 차이다. 이 호출 수 역시 실행 횟수나 전체 성능 차이의 단독 원인을 뜻하지 않는다.

기존 core runtime bundle에 원소 크기별 배열, 인덱스의 부작용, 인덱스 실행 도중 포인터 변경, 왼쪽 연산에 의한 RHS 값 변경, signed 값과 큰 unsigned 상수를 검사하는 회귀를 추가했다. 새 검사는 수정 전 컴파일러에서도 통과해 기존 의미를 확인했다. O0 및 언어 의미와 ABI는 바꾸지 않아 버전은 v15를 유지한다.

전체 검증에서는 기존 토큰 풀의 수명 오류도 발견했다. `lex_release_tokens`가 현재 풀을 해제해도 주소를 보관하고 있어, 다른 캐시 모듈의 중첩 제네릭 `>>` 처리에서 새 토큰을 해제된 공간에 쓰다가 충돌했다. 수정 전 컴파일러에서도 재현됐고 GDB로 호출 위치를 확인했다. [토큰 풀 오류 근거](token-pool-evidence.json)에 이전 컴파일러 해시, 작은 재현 소스와 종료 코드, GDB 호출 위치 및 수정 후 집중 검사 결과를 보존했다. 해제한 현재 풀의 주소, 길이, 용량을 초기화하고 기존 operator-name lifetime 검사에 풀 해제 후 토큰 생성과 다른 풀 해제 시 활성 풀 보존 검사를 추가했다. 이 수정은 파싱된 언어 의미를 바꾸지 않는다. 성능 표는 원래의 짝지은 측정값을 보존하며, 최종 컴파일러의 생성 코드 일치 여부를 별도로 확인한다.

## 조건과 한계

- Intel Core i7-7500U, Linux, 단일 논리 CPU 고정. 공유 호스트의 물리 코어를 독점한 측정은 아니다.
- GCC 11.4, Clang 15.0.7, NASM 2.15.05. 다른 버전의 컴파일러 성능을 대표하지 않는다.
- C++는 C++17 `-O3 -march=x86-64`. Bpp LLVM 출력에도 Clang `-O3 -march=x86-64`를 사용했다. C++ 최적화나 벡터화를 끄지 않았다.
- 모든 Bpp 프로세스에 4 GiB 주소 공간 제한. 컨테이너 전체에도 4 GiB 제한. 설치용 임시 네트워크는 측정 전에 분리했다.
- 세 번의 정답 검증 중 실제 크기 입력의 실행을 예열로 삼고, 이어서 각 조합을 5회 실행했다. 변형 순서는 매번 회전했다.
- GC 객체, 가변 `number`, 문자열 및 표준 컨테이너 구현 비교는 이번 고정 정수 배열 작업 범위에 포함하지 않는다.
- 반복 사이에 변동이 있고 일부 범위가 겹친다. [원시 기록](report.json)의 최소 및 최대값과 [그래프](comparison.png)의 오차 막대를 함께 봐야 한다. 오차 막대는 관측 범위이며 신뢰구간이 아니다.
- LLVM 열은 Bpp IR을 별도로 Clang O3에 전달한 결과다. `-llvm-build` CLI가 같은 옵션을 전달한다는 주장은 하지 않는다.

## 검증 상태

- 알고리즘 비교: 60개 조합 정답 검증, 실측 300개 통과.
- 집중 core 회귀: native/SSA O0/O1 및 LLVM 등 7개 통과, LLVM 제외 0개.
- 토큰 수명 수정 집중 검사: 3/3 통과. 기존 구현의 작은 재현 검사는 해제 후 남은 주소를 감지해 exit 10으로 실패했다.
- 최종 소스의 Windows 전체 검증 통과: Stage 1 == Stage 2 실행 파일 일치, 962/962 테스트, 기존 미지원 LLVM-only 1개 제외, 캐시 42/42 통과. 테스트 구간 435.7초, 프로세스당 4 GiB 제한.
- 최종 Windows Stage1/Stage2 SHA-256: `A6220EF779D33C8D48D37B70190C040E9F34072257054DD4C93780CA7FE4022B`.
- 최종 소스의 Linux 전체 `build_and_test.sh` 통과: 1,052/1,052 테스트, 실패 0개, LLVM 제외 0개. Stage 1 == Stage 2 어셈블리 일치와 최종 실행 파일 생성까지 완료했다. 4 GiB 주소 공간 제한과 컨테이너 4 GiB 제한, `TEST_JOBS=1`, 전체 프로필, 필터 없음으로 실행했다.
- 전체 검증을 통과한 최종 Linux 컴파일러로 10개 알고리즘을 다시 생성했다. 10개 모두 측정 당시 native 어셈블리 해시와 정확히 일치했고, 독립 기대값 검사 30개도 통과했다. [최종 생성 코드 대조](final-stage-verification.json)는 정답과 코드 일치 확인이며 성능 수치를 새로 측정해 교체한 기록은 아니다.
- 첫 Windows 긴 임시 경로의 실패 28개는 7개 파일 경로가 260~266자여서 모듈을 읽지 못한 결과다. 수정 전후 컴파일러가 동일하게 실패하는 것을 확인했다. 이 기록은 보존했고, 짧은 별도 작업 폴더에서 동일한 전체 검사를 다시 통과했다. 테스트나 기대값을 삭제하지 않았다.
- 첫 Linux 전체 실행은 `/dev/shm`의 실행 금지 설정으로 318개가 exit 126으로 실패했고, 위 토큰 풀 수명 오류로 1개가 컴파일 중 충돌했다. 실패 기록은 보존했다. 최종 전체 검사는 지원되는 `TEST_FAST_IO=0`으로 실행 가능한 작업 폴더를 사용했고, 수정된 토큰 수명 검사도 그대로 실행해 통과했다.

[검증 요약과 소스 해시](verification.json), [Linux 전체 로그](linux-full.log.gz), [Windows 전체 로그](windows-full.log.gz)를 보존했다. 작업 소스가 두 플랫폼에서 검증한 사본과 일치하는 것도 해시로 확인했다.

산출물 용량의 보수적인 상한은 소스와 계획, 측정 근거까지 포함해 약 9.43 GiB로 10 GiB 제한 이하다. [용량 집계](capacity.json)에 범위를 남겼다. 작업용 Linux 컨테이너는 종료했고, 설치용 임시 네트워크와 시작에 실패했던 작업용 컨테이너를 정리했다. 소스와 측정 근거 파일은 삭제하지 않았다.
