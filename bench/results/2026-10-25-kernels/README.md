# 배낭 DP와 행렬 곱셈 후속 최적화

이 자료는 앞선 최적화가 끝난 Bpp 컴파일러를 수정 전 기준으로 고정하고, 배낭 DP와 행렬 곱셈의 남은 차이를 조사한 결과다. 두 컴파일러가 같은 Bpp 입력을 컴파일한다. C++는 같은 알고리즘, 입력, 정수 폭과 결과 검사로 비교했다.

## 실행 시간

Intel i7-7500U의 논리 코어 하나에 고정한 Linux x86-64 환경에서 각 조합을 순서를 바꿔 5회 실행했다. GCC 11.4, Clang 15.0.7, NASM 2.15.05를 사용하고 어느 언어에도 CPU별 `-march=native` 옵션을 주지 않았다. 표의 값은 프로세스 CPU 시간 중앙값이며 단위는 ms다. 입력 생성, 배열 초기화, 프로세스 시작과 결과 출력이 포함된다. 컴파일 시간은 제외했다. C++ 열은 각 알고리즘에서 GCC O3와 Clang O3 중 빠른 중앙값이다.

| 알고리즘 | C++ | Bpp native O1 수정 전 | Bpp native O1 수정 후 | 실행 시간 감소 | Bpp LLVM과 Clang O3 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 배낭 DP | 6.592 | 33.865 | 30.728 | 9.3% | 6.565 |
| 행렬 곱셈 | 4.976 | 36.356 | 25.588 | 29.6% | 5.359 |

10개 알고리즘, 6개 실행 방식, 5회 반복으로 얻은 300개 실측값과 세 입력 크기의 정답 검사가 [원시 보고서](report.json)에 있다. [전체 요약](summary.tsv), [배낭 DP와 행렬 곱셈 비교 그림](kernel-comparison.png), [10개 알고리즘 그래프](comparison.png)는 동일한 보고서에서 생성했다. 배낭 DP는 5회 중 4회, 행렬 곱셈도 5회 중 4회에서 수정 후 시간이 짧았다. 합집합 찾기처럼 반복별 편차가 큰 항목은 5회 중앙값만으로 퇴행을 단정하지 않는다.

전체 검증이 끝난 뒤 CPU 간섭 없이 네 알고리즘을 15회씩 다시 교차 측정했다. 호스트 부하가 달라 절대 시간은 위 표와 다르므로, 이 표 안에서 수정 전후만 비교한다.

| 알고리즘 | 수정 전 | 수정 후 | 시간 감소 | 수정 후가 빠른 회수 |
| --- | ---: | ---: | ---: | ---: |
| 배낭 DP | 53.593 | 40.269 | 24.9% | 15/15 |
| 행렬 곱셈 | 59.433 | 39.771 | 33.1% | 15/15 |
| 벡터 내적 | 20.458 | 19.911 | 2.7% | 14/15 |
| 합집합 찾기 | 98.508 | 94.745 | 3.8% | 9/15 |

[15회 재측정 원시 보고서](repeat-report.json)는 각 반복의 시간과 정답 검사를 보존한다. 합집합 찾기의 개선 폭은 작고 실행별 변동이 커서 확정적인 개선으로 해석하지 않는다.

## 확인한 원인과 수정

- 비교 후 즉시 분기하는 조건식은 불리언 값을 만든 다음 다시 검사하던 명령을 제거했다. 임시 GC 프레임이 없는 함수의 64비트 정수 비교에만 적용한다.
- 호출과 부작용이 없는 64비트 정수 연산 및 고정 배열 읽기는 최대 5개 레지스터에서 왼쪽부터 계산한다. 조건에 맞지 않으면 기존 코드 생성 경로를 사용한다.
- `array[index] += value` 형태에서 인덱스와 오른쪽 식이 순수 정수식일 때 배열 주소를 한 번 계산해 읽기와 쓰기에 재사용한다. 기존 오른쪽 식의 부작용이나 별칭 순서가 필요한 경우는 최적화 대상에서 제외한다.

생성된 행렬 곱셈의 핵심 반복 구간은 정적으로 51줄에서 34줄, `push`와 `pop`은 각각 3회에서 1회로 줄었다. 배낭 DP의 핵심 구간은 46줄에서 38줄로 줄었다. [생성 코드 근거](codegen-evidence.json)에는 두 버전의 실제 어셈블리와 SHA-256을 남겼다. 정적 명령 수는 실행된 명령 수나 CPU 사이클과 같지 않다.

수정 후에도 행렬 곱셈의 native 실행 시간은 이 측정에서 가장 빠른 C++보다 약 5.14배 길다. Bpp 내부 반복은 여전히 스칼라 곱셈과 반복마다 배열 주소 계산을 사용한다. [이번 생성 코드 조사](codegen-evidence.json)에서 같은 입력의 GCC O3는 `pmuludq`와 `paddq`를 각각 9회, Clang O3는 각각 6회 포함했다. 벡터화와 반복 불변식 이동은 남은 차이를 조사할 다음 후보이며, 이 증거만으로 전체 시간 차이를 각 원인에 정확히 배분할 수는 없다.

## 검증

새 회귀 검사는 기존 core runtime 묶음에 추가했다. 수정한 컴파일러로 native와 SSA의 O0, O1, LLVM 경로 및 IR 검사 7개가 통과했다. Windows 전체 빌드에서는 Stage 1과 Stage 2 실행 파일의 SHA-256이 일치했고 962/962 테스트와 캐시 검사 42/42가 통과했다. LLVM 전용 미지원 항목 1개는 앞선 검증과 동일하게 제외됐다.

Linux 전체 `build_and_test.sh`도 Stage 1과 Stage 2 일치, 1,052/1,052 테스트, 실패 0개, LLVM 제외 0개로 종료 코드 0을 반환했다. 전체 검증을 통과한 최종 Linux 컴파일러는 10개 알고리즘 모두에서 측정 당시 native 어셈블리와 동일한 SHA-256을 생성했고, 독립 기대값 검사 30개를 통과했다. 모든 Bpp 실행에 4GiB 제한을 적용했다.

[검증 요약](verification.json), [Linux 전체 로그](linux-full.log.gz), [Windows 전체 로그](windows-full.log.gz), [최종 컴파일러 재검사](final-stage-verification.json), [Linux 산출물 해시](linux-artifact-hashes.json)를 보존했다.

작업 전 용량을 확보하려고 이전 Windows 검증 사본 두 곳에서 재생성 가능한 빌드 파일 658개, 817,043,513바이트를 정리했다. 소스, 테스트 입력, 로그와 측정 근거는 보존했다. 이후 별도 캐시 정리 시도는 자동 정책 검토에서 차단돼 삭제가 실행되지 않았다. 최종 보수적 집계는 약 9.55GiB로 10GiB 한도 이하다. [용량 집계와 정리 범위](capacity.json)에 기록했다.
